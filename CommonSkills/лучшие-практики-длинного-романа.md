# Лучшие практики V2: от вдохновения до распространения на нескольких платформах (вход через Prompt жанра + версия, управляемая гейтами)

> Область применения: все каталоги жанров этого репозитория (например, `женская-романтика/`, `городской-саспенс/`, `городская-магия-и-сверхспособности/` и т. п.).
>
> Основной принцип: **пользователь напрямую вызывает `.github/prompts/*.prompt.md` из каталога жанра, а не общий Skill.**

---

## 1. Сначала единая архитектура вызова (чтобы не сместить точку входа)

Работа идёт по такой цепочке:

`задача пользователя -> Prompt каталога жанра -> маршрутизация жанрового Skill -> основа общего Skill`

Это означает:

- В диалоге пользователь должен использовать названия возможностей жанровых Prompt (например, «анализ конкурентов», «проектирование плана», «SOP вывода на несколько платформ»).
- Не нужно заставлять пользователя говорить «вызови общий Skillобщий-xxx».
- `CommonSkills/` — это основание возможностей, а не вход со стороны пользователя.

Запоминается одной фразой: **пользователю говорим Prompt, система идёт через Skill.**

### 1.1 Ключевые отличия длинного романа и рассказа (чтобы не применить метод неверно)

И для длинного романа, и для сборника рассказов подходит рабочий процесс «гейт + возврат на доработку», но точки приложения разные:

- **Суть длинного романа**: сквозное продвижение через тома (главная линия, арки персонажей, давление финала постоянно нарастают).
- **Суть рассказа**: самостоятельная награда каждого рассказа + узнаваемость всего сборника (компоновка рассказов и единство стиля).

На практике для длинного романа сильнее подчёркиваются:

1. Продвижение на уровне томов и преемственность между томами (это не простое сложение «множества глав»)
2. «Холодные и горячие линии» и темп развязок (чтобы персонажи / линии не остывали)
3. Заблаговременные ограничения финала (чтобы поздние заплатки не превратились в обвал)

---

## 2. Сначала ответ на ключевой спор: правильно ли делать персонажей / настройки / реестры, пока общий план не оформлен?

**Вывод: можно, но только «лёгкую версию», без «тяжёлой окончательной версии».**

### 2.1 Почему нельзя слишком рано вкладываться

- Пока план нестабилен, цель главной линии, продвижение по томам и ограничения финала могут меняться.
- Если сначала тяжело переписывать персонажей / настройки / реестры, потом возникнут большие переделки, расхождения в формулировках и рассогласование улик.

### 2.2 Оптимальный способ: двухступенчатое моделирование

1. **До общего плана (лёгкая основа)**: оставляй только минимально жизнеспособную информацию
   - Персонажи: основное желание + ключевая слабость + главный конфликт отношений
   - Настройки: 3–5 жёстких правил (границы / цена / отказ)
   - Реестры: записывай только ключевые завязки, которые «главная линия обязана исполнить»
2. **После общего плана (тяжёлая окончательная версия)**: затем расширяй до полных биографий персонажей, настроек истории, реестра улик и завязок

## 3. Оптимальная форма всего процесса: 7 этапов, 6 гейтов (не прямая линия)

В отличие от «линейного девятишагового метода», V2 рекомендует процесс «этапы + гейты + циклы»:

0. Слой макроанализа рынка: макроанализ рынка (даёт рыночные доказательства для инициализации проекта)
1. Этап инициализации проекта: на основе макроанализа рынка выполняются калибровка платформы, коммерческая привязка, эмоциональное позиционирование, каркас метанастроек, адаптация модулей шаблонов
2. Этап конкурентов и дистилляции произведений (необязательно, проверка и уточнение после инициализации): анализ конкурентов — найти соперников; дистилляционное исследование — разобрать соперников
3. Исследовательский этап: вдохновение, позиционирование жанра
4. Этап архитектуры: общий план и каркас томов
5. Этап моделирования: окончательное оформление персонажей / настроек / реестров
6. Этап производства: создание текста, рецензия и возврат на доработку
7. Этап выпуска: оценка подписания, сборка пакета, распространение на нескольких платформах и возврат данных

### Слой макроанализа рынка (предшествует инициализации проекта, обязателен)

До инициализации проекта необходимо сначала завершить макроуровневый анализ рынка. Результат этого слоя напрямую становится входом для решений в инициализации.

Вызови `общий-глубокое-исследование` для макроуровневого исследования трендов, анализа экосистемы и изучения портрета читателя по целевой платформе × жанру, чтобы ответить на вопрос «что сейчас происходит на рынке в этом направлении».

- **Области исследования**: исследование трендов жанра + исследование экосистемы платформ + исследование читателей / рынка
- **Вывод**: отчёт об исследовании сохраняется в каталог `исследования-письма/`
- **Рекомендуется как обязательный**: при написании новой книги настоятельно рекомендуется выполнять. Если уже есть надёжная база исследований, можно пропустить.

Уже имеющиеся макроисследования можно использовать повторно в новом проекте, не нужно каждый раз исследовать заново.

### Этап инициализации проекта (обязателен перед началом работы, принимает макроанализ рынка)

После завершения макроанализа рынка и до проектирования плана сначала вызови `общий-инициализация-проекта` для стратегического планирования на уровне проекта. **В процессе инициализации главным основанием для решений служит результат макроанализа рынка**:

| Модуль инициализации | Основное основание решения | Источник сведений |
| --- | --- | --- |
| Конкурентное позиционирование в модуле 1 «Калибровка адаптации к платформе» | Исследование экосистемы платформ и данные о трендах жанра | Макроанализ рынка (исследования-письма/) |
| Модуль 3 «Эмоциональное позиционирование читателя» | Портрет читателя и поведенческие особенности | Макроанализ рынка (исследования-письма/) |
| Модуль 4 «Адаптация модулей шаблонов» | Судейский источник жанра и ограничения платформы | Макроанализ рынка + судейский источник жанра |
| Проверка дифференциации в модуле 7 «Проверка осуществимости» | Комплексное суждение о рыночном позиционировании | Макроанализ рынка |

Если в процессе инициализации обнаруживается нехватка данных о конкурентах, `общий-инициализация-проекта` автоматически вызовет `общий-анализ-конкурирующих-произведений`, чтобы дополнить перечень разрывов с конкурентами (в этом случае анализ конкурентов выступает дополнением и позже может быть проведён отдельно и глубже).

Через жанровые обёртки (например, `городской-саспенс-инициализация-проекта`, `женская-романтика-инициализация-проекта`) маршрутизация идёт на общую основу, выдаётся «синяя книга инициализации проекта».

> Пример входной команды: `/инициализация-проекта --platform 起点 --genre 都市悬疑` (или напрямую быстрая команда `/init`)

### Этап конкурентов и дистилляции произведений (необязателен после инициализации, проверка и уточнение)

После завершения инициализации проекта направление и решение определены. Теперь можно вызвать анализ конкурентов и дистилляционное исследование как проверку и уточнение позиционирования:

#### Анализ конкурентов (найти соперников)

Вызови `общий-анализ-конкурирующих-произведений`, чтобы зафиксировать на целевой платформе пул-кандидатов топ-10 того же жанра, по четырёхслойной рамке глубоко разобрать 3–5 ключевых сильных образцов и выдать сопоставимые отчёты анализа конкурентов.

- **Главное внимание**: какие комбинации шаблонов использовали конкуренты, настоящая обратная связь читателей в разделе рецензий / «слов к главе», насыщенность рынка и пространство дифференциации.
- **Вывод**: по каждому конкуренту отдельный отчёт, сохраняемый в каталог `竞对分析/`.

#### Дистилляционное исследование (разобрать соперников)

Для сильных образцов, выявленных при анализе конкурентов, вызови `общий-дистилляция-исследований-письма` или `общий-дистилляция-чертежа-произведения`, чтобы извлечь переиспользуемую повествовательную архитектуру и отпечатки шаблонов.

- **Дистилляция писательских исследований**: извлекает исполнимые ограничения из отчётов о писательских исследованиях уровня «жанр × платформа» и выдаёт шаблон писательского исследования.
- **Дистилляция образца произведения**: выделяет «ДНК повествовательной архитектуры» и отпечатки шаблонов удачного произведения и выдаёт шаблон образца произведения (отпечаток начала главы, закономерность ротации хуков, интервалы наград, распределение темпа, конфигурация шаблонов). Например: `蒸馏《诡秘之主》前100章作为蓝本`.

Оба вывода дистилляции единообразно регистрируются в `Agents.md` в корне проекта.

**Связь трёх слоёв**: макроанализ рынка отвечает на вопрос «стоит ли входить в эту нишу» — это решение о направлении до инициализации; анализ конкурентов отвечает на вопрос «какие на рынке сейчас пустоты и кто соперники» — это проверка и уточнение после инициализации; дистилляционное исследование отвечает на вопрос «какие закономерности у хороших произведений и как их использовать». Три слоя поэтапно сужают, но анализ конкурентов и дистилляционное исследование не влияют на сами решения о направлении в инициализации.

### Дистилляция стиля (подготовка письма перед созданием текста, необязательно)

- **Дистилляция авторского стиля** (`общий-дистилляция-авторского-стиля`): выделяет «ДНК письма» целевого писателя и выдаёт шаблон авторского стиля (базовая длина фраз, ритм абзацев, предпочтения в чувствах, предпочтения в ремарках диалога, отпечаток метафор, список запретов). Например: `蒸馏猫腻的文风，分析《庆余年》和《间客》`.

В отличие от дистилляции образца произведения на этапе конкурентов и дистилляции, дистилляция стиля не служит коммерческим решениям, а служит только конкретному исполнению письма. Достаточно выполнить её перед началом создания текста.

### Гейт G1 (макроанализ рынка + инициализация -> исследование конкурентов / исследование)

- Макроанализ рынка завершён, отчёт об исследовании сохранён в каталог `исследования-письма/`
- Все семь измерений решений в «синей книге инициализации проекта» завершены
- Продающий пункт можно пересказать одной фразой
- Рыночное позиционирование на целевой платформе ясно
- Обещание первых 3 глав начала исполнимо

### Гейт G2 (архитектура -> моделирование)

- Общий план V1 можно разбить на главы и вести как сериал
- Темп старта томов реализуем
- Ключевые точки наград определены

### Гейт G3 (моделирование -> производство)

- Персонажи / настройки / реестры согласованы с общим планом
- Нет явных конфликтов или обрывов цепочек
- Могут напрямую поддержать работу над главами

### Гейт G4 (производство -> выпуск)

- Качество глав соответствует планке (захват в начале / награда в середине / хук в конце главы)
- Цикл рецензий замкнут
- Материнский текст стабилен и пригоден для адаптации

## 4. Пример жанра «Женская романтика» (по порядку V2)

Ниже на примере `женская-романтика/` приведена рекомендуемая цепочка выполнения. Для других жанров нужно заменить Prompt по той же структуре.

### A. Исследовательский этап: позиционирование вдохновения

Используй Prompt:

- `женская-романтика/.github/prompts/проектирование-позиционирования-жанра.prompt.md`
- `женская-романтика/.github/prompts/проектирование-плана.prompt.md`
- `женская-романтика/.github/prompts/проектирование-названия.prompt.md`
- `женская-романтика/.github/prompts/написание-аннотации.prompt.md`

> **Связь исследовательского этапа со слоем макроанализа рынка**: слой макроанализа рынка до исследовательского этапа уже определил направление, а этап инициализации проекта уже утвердил решение, поэтому позиционирование жанра и проектирование вдохновения на исследовательском этапе могут напрямую ссылаться на эти результаты. Если в ходе исследования обнаруживается нехватка какой-то линии сведений (например, недостаточно образцов конкурентов), можно вернуться на этап конкурентов и дистилляции произведений, дополнить поиск и затем продолжить.
>
> **Каркас позиционирования жанра** рекомендуется выполнять после слоя рыночной разведки — сначала рыночной разведкой выяснить направление и пустые ниши, а затем каркасом позиционирования жёстко зафиксировать главный продающий пункт. Если общий план уже написан, а позиционирование всё ещё расплывчато, его можно доделать и на этапе архитектуры.

Результаты:

- Обещание одной фразой
- Цели первых 3 глав начала
- Дифференцированное позиционирование по отчёту анализа конкурентов

### B. Этап архитектуры: сначала общий план, затем тома

Используй Prompt:

- `женская-романтика/.github/prompts/проектирование-плана.prompt.md`
- `женская-романтика/.github/prompts/рецензия-плана.prompt.md`
- `женская-романтика/.github/prompts/цикл-рецензии-плана-sop.prompt.md`

Требования:

- Сначала довести общий план и тома до «исполнимого» состояния, и только потом переходить к тяжёлому моделированию материалов.

### C. Этап моделирования: тяжёлое окончательное оформление персонажей / настроек / реестров (после общего плана)

Используй Prompt:

- `женская-романтика/.github/prompts/написание-биографии-персонажа.prompt.md`
- `женская-романтика/.github/prompts/рецензия-биографии-персонажей.prompt.md`
- `женская-романтика/.github/prompts/проектирование-настроек-истории.prompt.md`
- `женская-романтика/.github/prompts/рецензия-настроек-истории.prompt.md`

Требования:

- Биографии персонажей и документы настроек должны служить плану, уже прошедшему гейты, а не быть самоцельным самолюбованием.

### D. Этап производства: замкнутый цикл глав + шлюзы качества

Используй Prompt:

- `женская-романтика/.github/prompts/создание-основного-текста.prompt.md`
- `женская-романтика/.github/prompts/цикл-создания-главы-sop.prompt.md`
- `женская-романтика/.github/prompts/шлифовка-основного-текста.prompt.md`
- `женская-романтика/.github/prompts/устранение-духа-ии.prompt.md`
- `женская-романтика/.github/prompts/рецензия-текста-главы.prompt.md`

Требования:

- Рецензия -> переписывание -> повторная рецензия обязательно сохраняются в файлы, а не остаются советами в чате.

### E. Этап выпуска: оценка подписания -> сборка пакета -> вывод и распространение на нескольких платформах

Используй Prompt:

- `женская-романтика/.github/prompts/评估签约概率.prompt.md` (целевая платформа определяется конфигурацией проекта)
- `женская-романтика/.github/prompts/组包投稿材料.prompt.md`

- Поддерживаются продвинутые возможности: параллельное распространение на несколько платформ, восстановление с точки обрыва, отслеживание по уникальному ключу главы.

- Англоязычные платформы: WebNovel, My Fiction, GoodNovel

Рекомендуется понимать распространение как три слоя:

1. **Слой оркестрации**: `多平台输出SOP` определяет порядок «сначала очистка материнского текста, затем платформенное переписывание, затем загрузка и распространение»
2. **Слой исполнения**: вызывается `распространение-романов/распространение-{платформа}/SKILL.md` для входа, заполнения текста, сохранения черновика / публикации
3. **Слой записи обратно**: статус главы, ссылка на платформе, причины сбоя, записи о повторных попытках записываются обратно в журнал распространения

Напоминание о границах каталога: `распространение-романов/` — это каталог процесса распространения (не каталог жанра); стабильные возможности, переиспользуемые между жанрами, следует вернуть в `CommonSkills/`.

Требования:

- Строго выполнять: очистка материнского текста -> адаптация под платформу -> вывод на платформу -> распространение на платформу.
- Версии для платформ должны «по-настоящему дифференцироваться», а не быть одним текстом в другой обёртке.

**Рекомендуемые пояснения (подробно):**

- **Создание глав**:
  - Рекомендуется в одной сессии одной командой подряд написать несколько глав (например, «подряд сгенерируй главы 6–10»), так проще сохранять связность сюжета и согласованность контекста.

- **Вывод на несколько платформ (переписывание / адаптация)**:
  - Рекомендуется «одна сессия обрабатывает версии только одной главы для нескольких платформ», то есть каждая сессия сосредоточена на одной главе и выдаёт все её платформенные версии (например, версии главы 7 для Fanqie, Qimao, Zhihu и т. д.). Так можно обеспечить, чтобы стиль переписывания, объём и требования к содержанию каждой платформы были тщательно подогнаны под эту главу, что удобно для сравнения и контроля качества.
  - Если нужно пакетно обработать несколько глав для нескольких платформ, можно одновременно открыть несколько сессий, каждая из которых отвечает за вывод разных глав на несколько платформ (например, сессия А обрабатывает главу 7, сессия Б — главу 8), добиваясь параллельного ускорения.
  - Преимущество такого подхода: контекст каждой сессии сфокусирован, удобно отслеживать различия и проблемы каждой главы на разных платформах, меньше путаницы.

- **Этап распространения (загрузка в админку платформы)**:
  - Поскольку для распространения на большинстве платформ требуются вход, капча, ручные подтверждения и т. п., рекомендуется «одна сессия сосредоточена на загрузке нескольких глав на одну платформу», то есть каждая сессия отвечает только за одну платформу, но может пакетно загружать несколько глав (например, за раз загрузить главы 6–10 на Fanqie).
  - Преимущество в том, что нужно один раз войти и один раз пройти проверку, затем можно подряд загружать несколько глав, что сильно повышает эффективность и уменьшает повторные проверки и прерывания из-за частого переключения платформ или сессий.
  - Если нужно распространять на несколько платформ, можно обрабатывать их в разных сессиях (например, сессия А отвечает за Fanqie, Б — за Qimao, В — за Zhihu), и в каждой сессии пакетно загружать главы.

- **Итог**:
  - При выводе на несколько платформ рекомендуется «в каждой сессии одна глава для нескольких платформ», при этом разные главы можно вести параллельно в нескольких сессиях.
  - При загрузке для распространения рекомендуется «в каждой сессии одна платформа с несколькими главами», при этом разные платформы можно вести параллельно в нескольких сессиях.
  - Так обеспечивается и целенаправленность адаптации содержания, и эффективность распространения, и удобство ручных операций.

## 5. Операционный возврат: направить данные распространения обратно в создание (на этом шаге спотыкаются многие команды)

После распространения на несколько платформ работа не «завершена», а переходит во входные данные следующего цикла оптимизации:

### 5.1 Свод читательской обратной связи и сигналов дочитывания / продолжения (по платформам)

- Доля дочитывания, доля продолжающих читать, распределение точек обрыва чтения (по главам и томам)
- Частотные ключевые слова в комментариях (персонажи, конфликт, темп, эмоциональная награда)
- Триггеры репостов / закладок (какие абзацы вызывают распространение)

### 5.2 Выявление сцен с сильной обратной связью и абзацев со слабой

- **Сильная обратная связь**: высокое дочитывание + высокое обсуждение, выделить «копируемые зацепки»
- **Слабая обратная связь**: низкое дочитывание + низкое обсуждение, найти «участки потери скорости / остывания»
- **Неожиданные хиты**: содержание, получившее высокий накал вне плана, оценить, не включить ли его в главную линию тома

### 5.3 Запись обратно в ресурсы следующего цикла создания

- Запись обратно в: план следующего тома (темп, плотность конфликтов, хук конца тома)
- Запись обратно в: контрольные карточки глав (захват начала, награда в середине, драйвер конца главы)
- Запись обратно в: стратегию продвижения отношений персонажей (давление на «горячих» персонажей, возвращение тепла «холодным»)

Именно этот шаг определяет, получится ли у вас устойчиво итерируемый двигатель сериала.

## 6. Частые заблуждения и исправления

1. **Ошибочно принимать общий Skill за вход пользователя**
   - Исправление: со стороны пользователя вход всегда через `prompt` из каталога жанра.

2. **Тяжело моделировать персонажей / настройки / реестры, пока общий план нестабилен**
   - Исправление: сначала лёгкая основа, пройти G2, потом тяжёлая окончательная версия.

3. **Рецензия даёт только советы в чате и не сохраняется в файлы**
   - Исправление: отчёты рецензий, действия-патчи и выводы повторной рецензии обязательно сохраняются.

4. **Слишком раннее распространение на несколько платформ**
   - Исправление: сначала сделать материнский текст устойчивым, затем выполнять `оркестрация-вывода-на-платформы-sop.prompt.md`.

5. **Порядок редактирования перевёрнут**
   - Исправление: сначала уровень структуры / развития, затем уровень языка, в конце уровень корректуры.

6. **Потеря контроля над темпом томов (остывание средних томов)**
   - Исправление: для каждого тома задавать «точку награды тома + точку драйвера конца тома», внутри тома каждые 5–8 глав проводить проверку темпа.

7. **Натянутая преемственность между томами (будто сменили книгу, а не том)**
   - Исправление: в конце предыдущего тома заранее заложить основное противоречие следующего тома, а в первых 2 главах следующего тома выполнить «краткое повторение + повышение + новое обещание».

## 8. Калибровка по внешним методологиям (ключевые пункты этой проверки через интернет)

Консенсус, найденный в интернете при этой проверке (используется для калибровки этого процесса):

- **Персонажи и сюжет должны быть связаны**: настройки персонажей должны служить развитию истории, а не быть изолированным нагромождением материала.
- **Порядок редактирования — сначала макро**: сначала уровень структуры и развития, затем уровень фраз, затем технический уровень корректуры.
- **Время внешней читательской обратной связи**: рекомендуется передавать Beta / внешнюю рецензию как минимум после достаточно основательного второго черновика.
- **Сериал лучше вести вложенными блоками**: сцена -> глава -> арка, послойное продвижение с сохранением места для корректировки направления и итераций.

Это согласуется со схемой V2 этого репозитория «гейты + лёгкое / тяжёлое разделение + возврат».

## 9. Заключение

Цель этих лучших практик V2 — не просто «дописать», а превратить вдохновение в устойчивую производственную линию.

Достаточно помнить две фразы:

1. **Вход всегда в Prompt жанра, а не в общий Skill.**
2. **До общего плана — лёгкое моделирование, после общего плана — тяжёлое окончательное оформление, после распространения — возврат данных.**

Тогда от первой главы до распространения на нескольких платформах процесс будет устойчивее, переделок меньше, итерации быстрее.

### 10.1 Шаг первый: создать рабочий каталог романа

Пример каталога: `D:\小说项目\她不再回头\`

### 10.2 Шаг второй: создать junction в рабочем каталоге романа (Windows)

Перейдя в `她不再回头/`, выполни следующие 5 команд:

- `mklink /j .github путь к каталогу .github соответствующего жанра в этом проекте`
- `mklink /j исследования-письма путь к каталогу исследования-письма соответствующего жанра в этом проекте`
- `mklink /j scripts путь к каталогу scripts этого проекта`
- `mklink /j распространение-романов путь к каталогу распространение-романов этого проекта`

Например, если текущий жанр — женская романтика, то `.github` и `исследования-письма` должны указывать на соответствующие каталоги в `женская-романтика/`.

### 10.3 Шаг третий: открыть рабочий каталог романа в VS Code и затем вызывать

Дальше при выполнении нужно использовать:

- **Слеш-команды**: например, `/深度研究`, `/проектирование-позиционирования-жанра`, `/анализ-конкурирующих-произведений`, `/проектирование-плана`
- **Ссылки на контекст**: например, `#小说总大纲.md`, `#审阅意见/第06章审阅.md`

Не пиши команды в виде пути вроде `женская-романтика/.github/prompts/xxx.prompt.md`.

## 11. Первое дело: создать файл конфигурации проекта

После открытия рабочего каталога романа в VS Code **первым делом** создай или отредактируй `Agents.md` в корне рабочего каталога и зарегистрируй основную платформу вывода. `Agents.md` одновременно служит файлом регистрации «шаблона писательского исследования», «шаблона авторского стиля» и «шаблона образца произведения», выданных на этапе дистилляции.

```markdown
## 主输出平台
起点中文网
```

(Если в файле уже есть другие записи, например шаблон писательского исследования или шаблон авторского стиля, допиши запись об основной платформе вывода в конец того же файла.)

Эта запись автоматически обнаруживается ключевыми Skill — `общий-создание-основного-текста`, `общий-цикл-создания-главы`, `общий-шлифовка-основного-текста`, `общий-усиление-хука-конца-главы` и др.; Skill по соглашению об именах загружают соответствующий `общий-вывод-{платформа}` и объединяют специальные правила платформы с общими правилами создания. Если `Agents.md` не существует или основная платформа не зарегистрирована, все ключевые Skill возвращаются к платформонезависимому общему режиму по умолчанию.

После этого можно переходить к первому шагу рабочего процесса — слою рыночной разведки (дистилляция / анализ конкурентов).

## 11. Как писать при вызове (шаблон /команда + #ссылки)

### 11.1 Общий шаблон вызова (можно копировать прямо)

> /【название команды】
>
> Цель: одной фразой, что нужно завершить в этом раунде.
>
> Прочитай следующий контекст:
>
> - #файлА
> - #файлБ
>
> Ограничения этого раунда:
>
> - Что обязательно сохранить (например, линию роста, линию отношений, ключевые настройки)
> - Чего нельзя делать (например, не добавлять факты, не менять жёсткие правила мира)
>
> Требования к выводу:
>
> - В какой файл или каталог записать
> - Сколько версий нужно (например, основная + короткая)
> - В чате отвечать только сводкой, полный текст не вставлять

### 11.2 Минимальный список входных данных (чтобы не «недокормить»)

Каждый раз давай как минимум три из следующих четырёх видов информации:

1. **Объект**: какую книгу, какой том, какую главу обрабатывать.
2. **Основание**: #план, #текст, #персонажи, #настройки, #отчёт рецензии.
3. **Цель**: что нужно улучшить в этом раунде (захват, продолжение чтения, вероятность подписания, адаптация под платформу и т. п.).
4. **Ограничения**: что нельзя трогать (факты, хронология, роль персонажей, порог объёма).

## 13. Быстрый перенос на другие жанры (подробная версия)

При переносе приведённых примеров на `都市悬疑`, `赛博庞克`, `太空科幻` рекомендуется менять следующие структурированные пункты:

### 13.1 Ограничения жанра и запреты

| Измерение ограничений | Что менять |
| --- | --- |
| Тип конфликта | Заменить шаблоны конфликтов в примерах раздела 12 главным конфликтом жанра (например, цепочка улик в саспенсе, конфликт правил в фантастике) |
| Запретные элементы | В «ограничения этого раунда» шаблона раздела 11 добавить красные линии модерации платформ и запреты жанра |
| Границы стиля | Чётко определить плотность языка, степень реализма, долю объяснений настроек, чтобы избежать межжанрового дрейфа стиля |

### 13.2 Стратегия томов и глав

- Регулировать длину томов и плотность «взрывных точек» внутри тома по жанру (у «романов с точками удовлетворения» чаще, у саспенса больше опирается на улики)
- Корректировать тип «хука конца тома» (саспенс — эскалация загадки, фантастика — переворот правил)

### 13.3 Стратегия вывода и распространения по платформам

- Переупорядочить приоритет платформ по популярности жанра (сначала главное поле боя, затем платформы распространения)
- Использовать показатели операционного возврата из раздела 5, но заменить их частотными словами обратной связи этого жанра
- Для каждой целевой платформы привязать один фиксированный Skill распространения (расположен в `распространение-романов/распространение-{платформа}/`), чтобы ручное переключение между админками не приводило к потере статуса

### 13.4 Тонкая настройка акцентов рецензии

- Использовать рамку заблуждений из раздела 6, дополнив её специфическими рисками жанра.
- Для городского саспенса в первую очередь проверять: логические дыры, обрывы цепочки улик, недостаточную честность загадки.
- Для киберпанка / космической фантастики в первую очередь проверять: нестабильность настроек, перегрузку объяснениями, отсутствие цены правил.

Остальная структура (цель, основание, ограничения, вывод) остаётся без изменений.
