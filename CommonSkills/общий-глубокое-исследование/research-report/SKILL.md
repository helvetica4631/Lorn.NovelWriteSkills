# общий-глубокое-исследование-отчёт-об-исследовании

## Способ запуска
`/research-report`

## Процесс выполнения

### Шаг 1: найти каталог результатов
Найти в текущем рабочем каталоге `*/outline.yaml`, прочитать конфигурацию topic, research_domain и output_dir.

### Шаг 2: просканировать необязательные поля-сводки
Прочитать все JSON-результаты, извлечь поля, подходящие для показа в оглавлении (числовые, краткие показатели), например:
- market_share (доля рынка)
- reader_rating (оценка читателей)
- growth_trend (тренд роста)
- search_heat (поисковая популярность)
- publication_count (число произведений)

С помощью AskUserQuestion спросить пользователя:
- Какие поля-сводки показывать в оглавлении, помимо названия item?
- Предоставить динамический список вариантов (на основе реально присутствующих в JSON полей)

### Шаг 3: сгенерировать скрипт преобразования на Python
Сгенерировать в каталоге `{topic}/` файл `generate_report.py`; требования к скрипту:
- Читает все JSON в output_dir
- Читает fields.yaml для получения структуры полей
- Покрывает все значения полей каждого JSON
- Пропускает поля, значение которых содержит `[不确定]` (`[неопределённо]`)
- Пропускает поля, перечисленные в массиве uncertain
- Формирует отчёт в формате Markdown: оглавление (с якорными переходами + выбранные пользователем поля-сводки) + подробное содержание (по категориям полей) + **итоги переносимости в творчество**
- Сохраняет в `{topic}/report.md`

**Требования к формату оглавления**:
- Должен включать каждый item
- Для каждого item показываются: порядковый номер, название (якорная ссылка), выбранные пользователем поля-сводки
- Пример: `1. [Миграция предпочтений читателей](#миграция-предпочтений-читателей) - Тренд роста: ↑15% | Поисковая популярность: высокая`

#### Технические требования к скрипту (обязательно соблюдать)

**1. Совместимость со структурой JSON**
Поддерживаются два вида структуры JSON:
- Плоская структура: поля прямо на верхнем уровне `{"name": "xxx", "market_share": "xxx"}`
- Вложенная структура: поля в подсловарях категорий `{"市场数据": {"name": "xxx"}, "内容特征": {...}}`

Порядок поиска поля: верхний уровень → ключ отображения категории → обход всех вложенных словарей

**2. Многоязычное отображение категорий**
Названия категорий в fields.yaml и ключи JSON могут быть в любой комбинации (кит.–кит., кит.–англ., англ.–кит., англ.–англ.). Необходимо построить двустороннее отображение (китайские названия категорий — это литералы протокола, их считывает `research/validate_json.py`; русские названия можно добавлять как псевдонимы):
```python
CATEGORY_MAPPING = {
    "市场数据": ["market_data", "市场数据"],  # рыночные данные
    "内容特征": ["content_features", "内容特征"],  # особенности содержания
    "读者反馈": ["reader_feedback", "读者反馈"],  # обратная связь читателей
    "专业知识": ["domain_knowledge", "professional_knowledge", "专业知识"],  # профессиональные знания
    "人物特征": ["character_traits", "人物特征"],  # черты персонажей
    "场景细节": ["scene_details", "场景细节"],  # детали сцены
    "技法要素": ["technique_elements", "技法要素"],  # элементы техники
    "创作可迁移": ["transferable_insights", "创作可迁移"],  # переносимость в творчество
}
```

**3. Форматирование сложных значений**
- list of dicts: каждый dict форматировать как одну строку, пары ключ–значение разделять ` | `
- Обычный list: короткие списки соединять запятыми, длинные выводить с переносами строк
- Вложенный dict: рекурсивно форматировать, показывать через точку с запятой или переносы строк
- Длинные текстовые строки (более 100 знаков): добавлять перенос строки `<br>` или использовать формат blockquote для лучшей читаемости

**4. Сбор дополнительных полей**
Собирать поля, которые есть в JSON, но не определены в fields.yaml, и помещать в категорию «Прочая информация». Обратить внимание на фильтрацию:
- Внутренние поля: `_source_file`, `uncertain`
- Ключи верхнего уровня вложенной структуры: `市场数据`, `内容特征` и т. п.
- Массив `uncertain`: нужно показывать название каждого поля отдельной строкой, не сжимать в одну строку

**5. Пропуск неопределённых значений**
Условия пропуска:
- Значение поля содержит строку `[不确定]` (`[неопределённо]`)
- Название поля есть в массиве `uncertain`
- Значение поля — None или пустая строка

**6. Итоги переносимости в творчество (новое, обязательно)**
В конце отчёта обязательно создавать раздел **«Выводы и рычаги, пригодные для творчества»**, переводящий все находки исследования в практические рекомендации, которые романист может использовать прямо:
- Классифицировать на три уровня: «можно прямо использовать в тексте», «можно использовать в настройках / плане», «требуют дальнейшего исследования»
- Каждая рекомендация должна быть конкретной: какую сцену можно написать, как использовать, в каких типах сюжетных эпизодов применить
- Это основная ценность всего отчёта исследования, пропускать или отписываться нельзя

### Шаг 6: самопроверка качества отчёта (контрольная точка 3)

После завершения генерации отчёта выполнить следующий контрольный список самопроверки (по методологии проверки качества Phase 4 nuwa-skill):

```markdown
## Контрольный список самопроверки качества отчёта

### Полнота структуры
- [ ] Содержит `## Тема исследования`
- [ ] Содержит `## Методы исследования и источники`
- [ ] Содержит `## Основные находки` (с разделением на три уровня: основные / справочные / для проверки)
- [ ] Содержит `## Выводы и рычаги, пригодные для творчества` (≥3 конкретных рекомендации)
- [ ] Содержит `## Честные границы` (дата отсечения информации + пробелы информации + неопределённые пункты + общая оценка уверенности)
- [ ] Содержит `## Источники информации` (с различением первичных / вторичных, с пометкой достоверности)

### Проверка качества (тройная верификация)
- [ ] У каждой «основной находки» есть поддержка ≥2 независимых источников?
- [ ] Каждая рекомендация в «Выводах и рычагах, пригодных для творчества» конкретна до уровня «какую сцену можно написать / как использовать / в каких эпизодах»?
- [ ] Более 50 % основных находок прошли проверку «различающая способность» (не банальность)?

### Честные границы
- [ ] Явно указана дата отсечения информации?
- [ ] Перечислены все пункты `[不确定]` и `[待验证]`?
- [ ] Дана общая оценка уверенности (высокая / средняя / низкая) с причинами?
- [ ] Отмечены измерения с нехваткой информации?

### Обработка противоречий
- [ ] Противоречивые находки в отчёте сохранены (не унифицированы принудительно)?
- [ ] Обе стороны противоречия снабжены типом источника и достоверностью?
```

### Шаг 7: спросить путь сохранения отчёта
С помощью AskUserQuestion спросить пользователя:
- В какой каталог сохранить отчёт? (рекомендуется сохранить в `исследования-письма/` каталога проекта или жанра)
- Нужно ли одновременно создать краткую версию (только «Выводы и рычаги, пригодные для творчества»)?

### Шаг 8: выполнить скрипт
Запустить `python {topic}/generate_report.py`

## Вывод
- `{topic}/generate_report.py` — скрипт преобразования
- `{topic}/report.md` — полный отчёт исследования
- `{каталог исследования-письма}/{краткое_название_домена}_{краткое_описание_темы}.md` — итоговый файл для сохранения (по желанию — краткая версия)
