# Подробные контрольные точки процесса выполнения

> Источник: контрольные точки каждой Phase и структура архивного пакета в SKILL.md § «Процесс выполнения»

## Phase 0.5: создание самодостаточного архивного пакета дистилляции

Перед основным извлечением обязательно создать или подтвердить в корневом каталоге целевого романного проекта архивный пакет дистилляции этого раунда:

```text
蒸馏产物/写作研究模板/[题材名]-[平台名]-исследования-письма档案/
   sources/                         # копии исходных отчётов, текст, забранный по URL, архив результатов сетевого поиска, индекс материалов, указанных пользователем
   references/research/              # записи извлечения по каждому отчёту, обязательно сохранять в файл
      01-来源索引.md
      02-文笔类约束提取.md
      03-结构类约束提取.md
      04-人物类约束提取.md
      05-禁忌类约束提取.md
      06-冲突与低置信字段.md
   synthesis/                        # слияние и удаление дублей, решения по конфликтам, пояснения по уверенности
   validation/                       # «сухой прогон» нижестоящих и проверка исполнимости
```

### Жёсткие требования

- Итоговый основной шаблон по-прежнему записывается в `蒸馏产物/写作研究模板/[题材名]-[平台名]-写作研究模板.md`, чтобы его удобно было регистрировать в `Agents.md` и читать нижестоящим.
- Каждое ограничение обязано прослеживаться до отчёта-источника, главы, URL или источника сетевого поиска; ограничения без источника в итоговый шаблон записывать нельзя.
- Источник по URL сначала нужно забрать как основной текст страницы; если в основном тексте страницы есть последующие ссылки, непосредственно связанные с этим исследованием, нужно продолжить забирать связанные ссылки и записывать уровень. Нельзя дистиллировать только по аннотации страницы.
- **Правила обработки источников сетевого поиска**:
  - После выполнения поиска показать пользователю ссылки страниц результатов, заголовки и аннотации, пользователь отбирает, какие страницы включить в дистилляцию.
  - Выбранные веб-страницы обязательно сначала забирать целиком (включая основной текст, таблицы данных, рейтинги и иное содержательное), нельзя дистиллировать только по аннотациям результатов поиска.
  - После забора каждой страницы записывать: URL источника, ключевые слова поиска, время забора, заголовок страницы; включать в архив каталога `sources/`.
  - Для ограничений, извлечённых из содержимого сетевого поиска, в поле «источник» указывать `[网络搜索: 关键词]` (сетевой поиск: ключевые слова) + конкретный URL источника.
- Если источники конфликтуют, обязательно сохранять конфликт и отмечать решение, нельзя принудительно примирять в видимо единое правило.

## Phase 1.5: контрольная точка Review извлечения

Закончив извлечение по отчётам, сначала приостановиться и вывести однолистовую сводку качества извлечения, подтвердить, переходить ли к слиянию:

| Класс | Извлечено ограничений | Высокая уверенность | Средняя уверенность | Число конфликтов | Основные источники |
| --- | --- | --- | --- | --- | --- |
| Письмо | [N] | [N] | [N] | [N] | [Отчёт A/URL] |
| Структура | [N] | [N] | [N] | [N] | [Отчёт A/Отчёт B] |
| Персонажи | [N] | [N] | [N] | [N] | [Отчёт C] |
| Запреты | [N] | [N] | [N] | [N] | [Отчёт A] |

Обязательно одновременно перечислить:

- Список полей с низкой уверенностью: какие — лишь качественные выводы, не могут считаться жёсткими гейтами
- Список конфликтных полей: какие источники предъявляют разные требования (например, медленный разгон Qidian vs быстрый ритм Fanqie)
- Список невключённых полей: какое содержимое отчётов исключено из-за излишней расплывчатости

Пользователь подтвердил качество извлечения → переход к Phase 2; если источников недостаточно или конфликтов слишком много, сначала дополнить источники или ограничить диапазон платформы/жанра.

## Phase 2.5: контрольная точка подтверждения слияния

После слияния и удаления дублей итоговый шаблон сразу не писать, сначала вывести сводку слияния:

- Число окончательно сохранённых ограничений: сколько по письму / структуре / персонажам / запретам
- Слитые синонимичные ограничения: какие источники говорят по-разному, но фактически указывают на одно и то же ограничение
- Сохранённые конфликты: какие ограничения из-за различий платформ обязательно представлены рядом
- Исключённые расплывчатые рекомендации: привести характерные примеры и причины исключения
- Область применения для нижестоящих: какие Skill будут потреблять какие ограничения
- **Список кандидатов в слой принципов** — какие ограничения воспроизведены в ≥ 2 отчётах и могут быть повышены до принципов; какие поддержаны лишь одним отчётом и остаются правилами
- **Охват атрибуции «почему»** — доля жёстких гейтов и сильных ограничений, по которым завершена атрибуция по психологии читателя; без атрибуции в итоговый шаблон не записывать

Пользователь подтвердил стратегию слияния → переход к Phase 3. Если пользователь выбирает приоритет какой-то платформы (например «ориентироваться на Qidian»), вернуться к Phase 2 и перестроить приоритеты конфликтных полей.

## Phase 3: результат и регистрация

1. По формату шаблона сгенерировать файл шаблона исследования письма `.md`
2. Записать в `蒸馏产物/写作研究模板/[题材名]-[平台名]-写作研究模板.md` в корневом каталоге целевого проекта
3. В `Agents.md` в корневом каталоге целевого проекта добавить запись регистрации (если `Agents.md` не существует — создать)
4. Предоставить пользователю сводку дистилляции: число извлечённых ограничений, распределение уверенности, неохваченные измерения, отличия от существующего шаблона (если есть)

## Phase 4: проверка качества

Перед записью итогового шаблона обязательно выполнить три проверки:

1. **Проверка прослеживаемости источников**: случайно проверить 5 ограничений, подтвердить, что каждое можно вернуть к конкретному отчёту/URL/источнику сетевого поиска/главе; непрослеживаемые удалить или понизить до примечания.
2. **Проверка «сухого прогона» нижестоящих**: выбрать любую 1 нижестоящую задачу (например, создание контрольной карточки главы или усиление начала главы) и проверить, можно ли ограничения шаблона исследования письма напрямую перевести в исполнимые действия.
3. **Проверка обработки конфликтов**: проверить, нет ли непомеченных конфликтов по одному полю; если есть, обязательно добавить пояснение конфликта или запись решения пользователя.

### Критерии прохождения

| Пункт проверки | Критерий прохождения | Сигнал непрохождения |
| --- | --- | --- |
| Прослеживаемость | У каждого ограничения есть источник, глава или URL | Ограничения как будто написаны по опыту |
| Исполнимость | Нижестоящий Skill может напрямую исполнять по ограничению | Есть только пустые слова вроде «усилить вовлечение» |
| Прозрачность конфликтов | Различия платформ и противоречия отчётов явно помечены | Требования Qidian/Fanqie смешаны в одну запись |
| Честность уверенности | Основания высокой/средней/низкой уверенности ясны | У всех полей записана высокая уверенность |

Результат проверки обязательно записывается в `validation/` архивного пакета, а в итоговом шаблоне даётся «комплексная уверенность».

## Phase 5: двухагентная шлифовка

После прохождения проверки по умолчанию запускаются две независимые перспективы шлифовки (может имитировать основной исполнитель или выполнять дочерний Agent):

- **Agent A: рецензирование исполнимости ограничений** — проверить, может ли каждое ограничение быть потреблено `创建小说正文 / 生成章节控制卡 / 正文润色 / 审阅章节正文`.
- **Agent B: рецензирование источников и конфликтов** — проверить прослеживание источников, платформенные конфликты, поля с низкой уверенностью, полноту забора URL-ссылок и результатов сетевого поиска, полностью ли забрано содержимое страниц сетевого поиска, а не дистиллировано лишь по аннотациям.

Основной исполнитель сводит два мнения, принимая только изменения, повышающие «исполнимость / прослеживаемость / прозрачность конфликтов»; ради «наполнения» шаблона расплывчатые рекомендации не включать.

## Обновление существующего шаблона исследования письма

Когда пользователь говорит «обнови шаблон исследования письма», «добавь новый отчёт», «дополни только исследования платформы Douban»:

1. Сначала прочитать существующий шаблон исследования письма и архивный пакет, подтвердить список источников, число извлечённых ограничений, конфликтные поля и дату дистилляции.
2. Делать инкрементное извлечение только для нового каталога/файла/URL/содержимого сетевого поиска или отчётов платформы, указанных пользователем.
3. Сравнить старые и новые выводы:
   - Новый отчёт усиливает старое ограничение → дополнить источник и уверенность
   - Новый отчёт конфликтует со старым ограничением → пометить различия платформ/отчётов, не перекрывать напрямую
   - Новый отчёт даёт новое измерение → добавить поле и пометить новый источник
4. Обновить в шаблоне дату дистилляции, число источников, число ограничений, пояснения конфликтов и пояснение версии, не переписывая несвязанные поля.
5. На краю добавить «цепочку ключевых ограничений»: свести 3-5 самых важных ограничений в линейно исполнимый checklist, отсортированный по стадиям творчества

## Phase 0: определение источника

1. Если пользователь указал источник (каталог/файл/URL/сетевой поиск) → использовать указанный источник
2. Если пользователь не указал → сканирование по умолчанию (всё внутри романного проекта):
   - Корневой `исследования-письма/` романного проекта (если существует)
   - Корневой `调研报告/` романного проекта (если существует, равный с «исследования-письма/» приоритет)
   - Корневой `CommonSkills/исследования-письма/` романного проекта (если существует)
3. Результаты сканирования показать пользователю для подтверждения (перечислить все найденные файлы отчётов, заголовки, размер файла и дату)
4. **Если ни в источниках по умолчанию, ни в указанных источниках не найдено пригодных материалов**, спросить пользователя, включать ли сетевой поиск. После подтверждения пользователь даёт ключевые слова поиска (например «番茄小说 2026 都市悬疑 写作趋势»), Skill выполняет поиск и обрабатывает веб-страницы результатов как источники дистилляции.
5. Пользователь может из них отобрать/исключить/дополнить
