## Защита исполнения (жёсткие гейты)

### Подтверждение прочтения (обязательно)

**Этот файл — не резюме и не справочная подсказка, а инструкция процесса, которую нужно исполнять дословно.**

До любого вывода обязательно сначала по пунктам вывести следующее подтверждение. Если выводить содержимое основного текста без подтверждения — это в любом случае считается нарушением процесса:

```
[Подтверждение прочтения]
- Этот файл SKILL.md → [прочитан полностью, все жёсткие правила и обязательные требования полностью поняты]

- references/нормы-сводки-и-журнала-мультивывода.md → [прочитан и понят]
```

Если в корневом каталоге проекта есть `Agents.md` → дополнительно подтвердить полное прочтение (включая раздел `平台POV基线表`).

### Позиция исполнителя (жёстко)

- **Этот Skill — «исполнитель», а не «планировщик»**: цель — реально прогнать 15-шаговый замкнутый цикл до конца, а не выдать план, список платформ или промежуточный отчёт.
- **Одним духом**: начав выполнение, нужно за один проход выполнить пять этапов A→E, на полпути нельзя останавливаться и задавать вопросы, не относящиеся к задаче или выводимые по существующим правилам.
- **Запрещена пауза в духе «жду, пока скажешь продолжать»**: если не сработала жёсткая нехватка параметров (например, путь к главе не удаётся разобрать, в Agents.md нет таблицы платформенного POV), нельзя останавливаться в ожидании ответа пользователя.
- **Пошаговый вывод**: в начале каждого шага выводить `[Прогресс] Этап X / шаг N: описание текущего действия`; до завершения всех 15 шагов нельзя выводить «многоплатформенный вывод завершён» или итоговое резюме.

### Запрет самовольно пропускать шаги и запрет не загружать Skill (жёстко, новое)

1. **Заявление «вызвать skill» в каждом шаге — обязательный гейт, а не рекомендация** — если в шаге указано `调用 skill：общий-очистка-мастер-черновика` (вызвать skill) и подобное, необходимо реально загрузить через инструмент `skill()` SKILL.md соответствующего Skill и исполнять его инструкции дословно; нельзя пропускать загрузку, заменяя исполнение «имеющимися знаниями».
2. **Запрещено самовольно пропускать любые шаги** — все шаги от шага 1 до шага 15 выполняются по пунктам, нельзя пропускать под предлогом «этот шаг неприменим», «старые платформы уже выполнялись», «сходство достигнуто». Если какой-то шаг действительно неприменим (например, у платформы нет отдельного выходного Skill), необходимо явно записать в журнал `skipped_{stepName}_reason=xxx`, и должно быть явное основание в правилах.
3. **Запрещено пропускать загрузку skill «ручной заменой»** — нельзя под предлогом «я уже знаю содержимое этого Skill» не загружать через инструмент `skill()`. Каждое выполнение шага обязано заново загружать соответствующий файл Skill через `skill()`, чтобы получить актуальную версию.
4. **Запрещено подменять «шаг выполнен» фактом «файл уже существует»** — критерий: были ли при данном выполнении реально прочитаны, изменены, перезаписаны файлы и обновлён журнал.
5. **Пять шагов гейта этапа D обязательно выполнять по порядку** — порядок шагов 10→11→12→13→14 нельзя менять, объединять или пропускать. Любой непрошедший гейт обязан перейти в возврат на доработку (шаг 12), затем последовательно перепроверяться.

### Ситуации, которые запрещено нарушать (жёстко)

Любое из следующего составляет нарушение, необходимо вернуть на доработку или выполнить заново:

1. **Запрещено перепрыгивать шаги между главами или объединять шаги** — каждая глава обязана независимо и полностью выполнить 15-шаговый замкнутый цикл. Допускается оркестровка по фазовому конвейеру (например, пакетная предпроверка → по главам очистка, адаптация, сохранение в файл, гейты), но нельзя одной прикидкой / одним сохранением / одним гейтом покрывать много глав. Переходить к следующей главе только после независимого прохождения всех платформенных гейтов.
2. **Запрещено генерировать основной текст скриптами** — скрипты используются только для проверки гейтов / подсчёта знаков / проверки сходства, содержимое основного текста обязано генерироваться ИИ-моделью.
3. **Запрещено загрязнение шаблонными предложениями** — не должно быть механических групп предложений «абстрактное самоповествование + шаблон глагола + канцелярское существительное» или указанных загрязняющих фраз.
4. **Запрещено перерезание фиксации взгляда** — зафиксированный `platformPovContract` нельзя самовольно менять лицо повествования в последовательных главах.
5. **Запрещено пропускать узел очистки или адаптации** — нельзя пропускать `общий-очистка-мастер-черновика` или `общий-адаптация-под-платформы`.
6. **Запрещено писать сразу, пропуская прикидку** — каждый узел «глава × платформа» обязан сначала сформировать платформенный эскиз прикидки, затем переходить к переписыванию основного текста.
7. **Запрещено расширять возврат на доработку** — возврат на доработку одной платформы не должен тянуть назад другие уже прошедшие платформы.
8. **Запрещено пропускать с нарушением норм** — если любой из гейтов — знаков/POV/сходства/качества — не пройден, объявлять завершение нельзя.

## Основные красные линии (жёсткие ограничения, нарушать абсолютно нельзя)

### Красная линия 0: гейт знаков (динамическое чтение, приоритет — переопределение уровня проекта)

- Гейт знаков больше не использует глобальные жёстко заданные значения. Целевое число знаков определяется по следующим приоритетам (от высшего к низшему):
  1. **Переопределение уровня проекта**: прочитать `Agents.md` в корне проекта, если в нём есть требования к числу знаков по **конкретной платформе** (например `起点：{ bodyCJK: 3000-5000, afterwordCJK: 200-300 }`), то ориентироваться на них.
  2. **Значение основной платформы по умолчанию**: если в `Agents.md` конкретная платформа не указана, но задано требование к числу знаков основной выходной платформы, то определяется по «диапазону знаков платформы по умолчанию» в `общий-вывод-*/SKILL.md` основной выходной платформы.
  3. **Значение целевой платформы по умолчанию**: прочитать «диапазон знаков платформы по умолчанию» в `общий-вывод-*/SKILL.md` целевой платформы этого раза.
- До начала любой платформенной рассылки обязательно сначала для **каждой главы × каждой платформы** построить суждение о выполнимости по числу знаков; если основной текст и `## 作者有话说` не достигают целевого числа знаков платформы, рекомендуется сначала восполнить, и только затем переходить к стадии написания платформенного основного текста.
- Если сам исходный текст короток, обязательно сначала вызвать `общий-очистка-мастер-черновика`, затем решить, нужно ли усиление исходника; если после усиления исходника всё ещё далеко ниже порога знаков целевой платформы, можно остановить ветку этой платформы, записать `blocked_word_count_insufficient`, нельзя платформенной постобработкой «добирать знаки».
- Порядок обработки нехватки знаков обязательно такой: **сначала дополнить информацию и сцены → затем дополнить основной текст → затем дополнить «слово от автора» → лишь в последнюю очередь разрешается переходить к платформенным гейтам и финальной проверке сходства**. Запрещено оставлять нехватку знаков на временное исправление в платформенной ветке.
- На стадии платформенного эскиза обязательно явно записывать суждение о запасе знаков для этой платформы, вместе с источником целевого числа знаков (переопределение проекта / значение платформы по умолчанию).
- Если версия любой платформы после первого сохранения в файл всё ещё не достигла цели по знакам, рекомендуется вернуть на доработку и расширить, нельзя сначала сохранять короткую версию, «которая проходит гейты», а потом дописывать.

### Красная линия 1: полное выполнение по главам (допускается оркестровка многих глав, запрещены перескакивание шагов и снижение качества между главами)

**Оркестровка многих глав допускает повышение эффективности повторного использования контекста, но нельзя сокращать или пропускать ни одно звено ни одной главы.**

- **Каждая глава обязана независимо и полностью выполнить 15-шаговый замкнутый цикл** (очистка, адаптация, платформенное переписывание, проверка гейтов, финальная проверка сходства, определение завершения). Многоглавая оркестровка меняет порядок выполнения (продвижение по фазовому конвейеру), а не глубину выполнения каждой главы.
- **Допустимая оркестровка многих глав**: разом выполнить пакетную предпроверку и создать очередь задач → продвигаться «скользящим» фазовым конвейером «платформенная прикидка → платформенное сохранение → финальная проверка гейтами», в каждой фазе каждая глава независимо выполняет все подшаги, охватываемые этой фазой.
- **Запрещённые действия с перепрыгиванием шагов**:
  - Запрещено одним эскизом прикидки покрывать многие главы — каждая глава обязана независимо делать платформенную прикидку
  - Запрещено одним контрактом POV по умолчанию покрывать все главы — каждая глава обязана независимо подтверждать наследование или переключение POV
  - Запрещено считать «выполненным» одноразовое сохранение многих глав — каждая глава после сохранения обязана независимо пройти все четыре гейта
  - Запрещено сначала пакетно дописать все платформенные версии, а потом пакетно прогнать гейты — каждая глава обязана пройти все платформенные гейты, прежде чем перейти к следующей
- **Правильный способ**: пакетная предпроверка (разовая) → глава 1: очистка → адаптация → сохранение всех платформ → гейты всех платформ → пройдено → глава 2: очистка → адаптация → сохранение всех платформ → гейты всех платформ → пройдено → ……
- **Неправильный способ**: разом выполнить очистку для всех глав, затем разом адаптацию для всех глав, затем разом платформенное переписывание для всех глав, наконец разом прогнать гейты.
- **Любые проблемы качества содержимого, путаница сходства, отказ гейтов, вызванные нарушением этой красной линии, целиком ложатся на исполнителя**.

### Красная линия 2: многоплатформенные версии обязаны генерироваться ИИ (запрещены скриптовый мусор, запрещены пакетные шаблоны)

- **Абсолютно запрещено использовать скрипты для генерации случайных знаков, мусорного содержимого или бессмысленного наполнения знаками**.
- **Абсолютно запрещено использовать правила пакетной замены, библиотеки шаблонов или автоматизированные инструменты для пакетного переписывания основного текста**.
- **Содержимое многоплатформенной версии для каждой платформы обязано напрямую генерироваться вызовом ИИ-модели, обеспечивая высокое качество, высокую креативность, соответствие платформенному стилю**.
- **Сгенерированное ИИ содержимое обязано быть оригинальным, логичным, с литературной фактурой текстом произведения, а не знаковым мусором или низкокачественной заменой**.
- **Единственное назначение скриптов: проверка гейтов, подсчёт знаков, проверка сходства, проверка качества**. Скрипты нельзя использовать для генерации содержимого.
- После завершения генерации ИИ обязательно проводить ручную перепроверку (проверка логики, согласованности, риска выпадения из текста), но само содержимое отвечает за генерацию ИИ.
- Выход, нарушающий эту красную линию (включая скриптовый мусор, пакетные шаблоны, низкокачественную генерацию ИИ), сдавать нельзя, всё обязательно вернуть на доработку и заново сгенерировать вызовом ИИ.
- Когда способность генерации ИИ недоступна (например, лимит субагентов, модель недоступна, сбой вызова), **единственное допустимое действие**: записать в журнал пометку `blocked_ai_unavailable` и остановить производство основного текста; абсолютно запрещено переходить на какое-либо скриптовое переписывание или запасной вариант с заменой по шаблону.

### Красная линия 3: нулевая терпимость к загрязнению шаблонными предложениями (новая жёсткая красная линия)

- Абсолютно запрещено появление в платформенном основном тексте механических групп предложений «абстрактное самоповествование + шаблон глагола + канцелярское существительное» (например «я здесь … сверить/выровнять …, в конечном счёте … формулировка/журнал …, лишь бы …»).
- Абсолютно запрещено появление семейства загрязняющих фраз: `对照项落在`, `先把同一句话拆碎`, `先把顺滑的解释拆开`, `只求能追溯`, `只求能复核`, `只求对得上`.
- При попадании в указанное загрязнение шаблонными предложениями обязательно признавать **жёстким провалом** и переписывать с возвратом на доработку; нельзя пропускать под предлогом «знаков достаточно» или «сходство в норме».
- Следующие скрипты нельзя включать в цепочку производства основного текста: `scripts/append_cn_unique_monologue.ps1`, `scripts/append_cn_unique_narration.ps1`, `scripts/append_cn_unique_thirdperson.ps1`, `scripts/rephrase_cn_body.ps1`, `scripts/rephrase_en_body.ps1`, `scripts/cn_lexicon_profile_transform.ps1`.

### Красная линия 4: фиксация взгляда в последовательных главах платформы (новая жёсткая красная линия)

- Для вывода последовательных глав одной платформы обязательно сначала зафиксировать `platformPovContract` этой платформы, содержащий как минимум: `expected(first|second|third)`, `lang`, `baselineSource`, `switchPolicy`.
- Источник `platformPovContract` по умолчанию обязан иметь такой приоритет: явное указание пользователя > ранее завершённые главы этой платформы > существующая цепочка взгляда исходника > первая прошедшая глава этой платформы в этой партии.
- Если у какой-то платформы уже есть действительный контракт POV, последовательные последующие главы обязаны его наследовать; абсолютно запрещено без явной причины и одобрения в журнале дописывать цепочку третьего лица глав 1–8 так, что в главах 9–15 она вдруг становится первым лицом, или наоборот дрейфовать.
- Менять разрешено только в трёх сценариях: исходная глава изначально является главой с переключением взгляда / последовательной главой многих точек зрения; пользователь явно требует для этой платформы перехода лица повествования; историческая цепочка платформы изначально была другой POV, а в этот раз лишь продолжение написания.
- Любое незарегистрированное изменение POV считается **жёстким провалом**: необходимо вернуть на доработку и переписать, а в журнале записать `pov_switch_without_approval` или `pov_drift_detected`.

### Красная линия 5: целевое число знаков не откладывать (пересмотрено до мягкой рекомендации)

- Не рекомендуется делать стратегией процесса «сначала сохранить в файл, потом добирать знаки» — это строит платформенные гейты, гейт сходства и гейт POV на неверной длине.
- Не рекомендуется сначала рассылать короткий текст на все платформы, а потом надеяться, что «слово от автора» или платформенные доработки где-то всё исправят.
- Если глава на какой-то платформе далеко ниже целевого числа знаков платформы, можно в журнале пометить ветку этой платформы `blocked_word_count_insufficient` и подумать о прекращении последующей рассылки по этой ветке.
- Целевое число знаков — справочный порог, а не жёсткая блокировка; он на одном уровне с гейтом контракта POV, но непрохождение автоматически не блокирует, решение о продолжении принимает рецензент.

## Контракт платформенного POV и гейт непрерывности (обязательно)

- В пакетных задачах с многими главами каждая платформа обязана сначала зафиксировать один `platformPovContract`; нельзя позволять каждой главе при платформенном переписывании ad hoc заново решать, «в этой главе удобнее первое или третье лицо».
- `platformPovContract` должен чётко записывать как минимум: `expected`, `lang`, `baselineSource`, `switchPolicy`; при необходимости восстановления с контрольной точки дополнительно записать `inheritedFromChapterNo` или эквивалентный источник.
- Если в каталоге целевой платформы уже есть завершённые предыдущие главы той же книги, той же части / тома, обязательно сначала прочитать последнюю прошедшую главу; при необходимости дополнительно посмотреть последние 2–3 главы, подтвердить имеющуюся цепочку POV этой платформы, затем продолжать писать.
- Если у целевой платформы ранее не было исторической цепочки, допускается создать контракт по «первой прошедшей главе этой платформы в этой партии»; после создания все последующие последовательные главы наследуют, пока не сработает допустимое условие переключения.
- Переключать разрешено только в трёх сценариях: исходная глава изначально является главой с переключением взгляда / последовательной главой многих точек зрения; пользователь явно требует перехода лица повествования для этой платформы; историческая цепочка платформы изначально была другой POV, в этот раз лишь продолжение по имеющейся цепочке.
- При попадании в допустимое переключение обязательно записать в журнал `switchApproved=true`, `switchReason`, `switchPlan`; без этих полей всё равно обрабатывается как несанкционированный дрейф.
- Если в цепочке третьего лица в блоке основного текста встречаются вне диалогов местоимения вроде `我 / 你 / I / you`, или в цепочке первого лица в блоке основного текста полностью отсутствуют якоря первого лица, это приоритетно считается провалом; нельзя объяснять «просто стиль гибче».
- Глава с переключением взгляда / последовательная глава многих точек зрения — не означает, что можно отказаться от контракта: они лишь повышают контракт с «единого POV на всю главу» до «исполнения по зарегистрированному плану переключения», по-прежнему запрещено на месте произвольно «менять оболочку».

## Формулировка исполнения гейта сходства (обязательно)

- Китайская группа: обязательно охватывать «попарное сравнение китайских платформ + сравнение каждой китайской платформы с исходной главой», порог `< 0.20` (рекомендуется `0.199`).
- Английская группа: обязательно охватывать «попарное сравнение английских платформ», порог `< 0.20` (рекомендуется `0.199`).
- Можно использовать `scripts/chapter_similarity_check.ps1`, чтобы прямо вычислять по группе путей, или `scripts/run_similarity_from_platform_config.ps1`, чтобы выполнять на основе платформенной конфигурации; но итоговый отчёт обязательно должен чётко разделять китайскую и английскую группы.
- Если в любой группе есть пара, превысившая порог, пропускать нельзя, обязательно вернуть на доработку и перепроверять, пока все не достигнут нормы.

## Гейт полноты вызовов (обязательно)

- При каждом выполнении обязательно выдавать «запись аудита вызовов», содержащую как минимум:
	- `requiredCalledSkills`: список Skill, которые должны быть вызваны в этой задаче (развёрнутый по главам и платформам)
	- `calledSkills`: список реально вызванных Skill (включая порядок вызова)
	- `missingCalledSkills`: список должных, но не вызванных
- `requiredCalledSkills` должен включать как минимум:
	- по 1 разу `общий-очистка-мастер-черновика` на каждую главу
	- по 1 разу `общий-адаптация-под-платформы` на каждую главу
	- по 1 разу соответствующий `общий-вывод-*` на каждую пару «глава × целевая платформа»
- Пока `missingCalledSkills` не пуст, эту задачу обязательно признавать незавершённой и продолжать возврат; в «сводку завершения» переходить нельзя.

## Сначала прикидка, потом письмо (обязательно)

- Для каждого узла «глава × платформа» перед фактической записью платформенного основного текста обязательно сначала сформировать **платформенный эскиз прикидки**.
- Этот эскиз служит только исполнению, в файл итогового основного текста записывать его нельзя; его минимальное содержимое включает как минимум:
	- Перечень основной информации исходной главы (предельно сжатые тезисы)
	- Перечень стилевых ограничений платформы
	- Нынешний контракт POV этой платформы (первое / второе / третье лицо, повествовательная дистанция, разрешено ли переключение)
	- Тенденцию заголовка и тенденцию хука
	- Планируемые действия по снижению повторов (например структурная перестановка, переписывание диалога, замена способа несения, перестройка ритма)
	- Какую информацию обязательно сохранить, какие выражения обязательно «сменить оболочку»
- Запрещено пропускать прикидку и сразу писать; также запрещено сначала писать нейтральную основу, а потом пакетно слегка править до платформенных версий.
- Прикидку можно выполнять последовательным размышлением, структурным эскизом, списком платформенных различий или эквивалентным внутренним способом исполнения, но обязательно соблюдать «сначала зафиксировать платформенный стиль, затем переходить к переписыванию основного текста».

## Дисциплина исполнения (обязательно)

- Начав исполнение, обязательно за один проход выполнить в порядке «нормализация входа → очередь задач → платформенная прикидка → сохранение по платформам → гейты и возврат → поязыковая финальная проверка → закрытие сводкой».
- Если исходник явно несёт тяжёлый платформенный тик или ключевые события / эмоциональная ось нестабильны, обязательно сначала вставить узел «очистка мастер-рукописи», нельзя размножать проблему без изменений на все платформенные ветки.
- Если не сработали четыре сценария — «не удаётся разобрать `chapterNo` / не удаётся стабильно вывести `分部目录` и `分卷目录` / пользователь дал только основной текст и нет необходимых метаданных / реальная ошибка исполнения делает невозможным следующий шаг», запрещено на полпути останавливаться и ждать, пока пользователь скажет «продолжай».
- Если за один раз обрабатывается много глав, обязательно сначала завершить пакетную предпроверку и очередь задач, затем продвигаться «скользящим» образом с «главой во внешнем цикле, платформой во внутреннем»; нельзя разом разворачивать все ветки «глава × платформа». - **Гейт полноты по главам при оркестровке многих глав**: многоглавая оркестровка допускает поэтапное продвижение (пакетная предпроверка → очистка по главам → адаптация по главам → сохранение по главам → гейты по главам), но каждая глава обязана независимо полностью выполнить все 15 шагов замкнутого цикла. Запрещено одной очищенной мастер-рукописью покрывать много глав, запрещено одноразовой прикидкой адаптации заменять прикидку по главам, запрещено считать одноразовое сохранение многоплатформенных версий многих глав свидетельством пройденных гейтов. Если в любом узле «глава × платформа» пропущено любое звено, всю партию объявлять завершённой нельзя.- Верхний предел параллелизма по умолчанию должен быть консервативным: одновременно продвигать не более 2 главных задач, не более 2 платформенных ветвей на главу, общее число активных платформенных ветвей в глобальном масштабе не более 4; как только среда перегружается или растёт риск конфликта журналов, обязательно автоматически понижать.
- Минимальная единица повторного использования при восстановлении с контрольной точки обязана быть узлом «глава × платформа»; узлы, уже записанные и полностью прошедшие гейты, пропускать напрямую, нельзя переделывать всю партию.
- После фиксации POV последовательных глав одной платформы в первую очередь наследовать последний прошедший узел; нельзя позволять разным главам «заново выбирать более удобное лицо».
- Каждый платформенный узел перед входом в финальную проверку сходства обязан сначала пройти «проверку обнуления загрязнения шаблонными предложениями»; если сработало семейство загрязняющих фраз, входить в финальную проверку сходства запрещено.
- Если сработал сценарий «способность генерации ИИ недоступна», обязательно выполнить: `остановить производство основного текста -> записать причину блокировки -> вывести минимальное действие восстановления`; нельзя продолжать «сначала сгенерировать скриптом, потом исправлять».

- Поля журнала, пути отчётов гейтов, провалившиеся узлы и следующие действия должны напрямую поддерживать восстановление с контрольной точки; нельзя оставлять ключевое состояние только в выводе чата.
- Борьба с водой, качество текста и согласованность стиля — предварительные гейты финальной проверки; при непрохождении любого обязательно сначала вернуться на доработку в соответствующую платформенную ветку.
- Непрерывность POV — тоже предварительный гейт финальной проверки; при несанкционированном дрейфе лица на любой платформе обязательно сначала вернуться в ветку этой платформы и исправить, и лишь затем допускается вход в финальную проверку.
- Гейт заголовка должен удовлетворять одновременно: не совпадать с названием исходной главы, не повторяться между платформами одной главы, нельзя переиспользовать старый скелет заголовка другой главы, меняя лишь номер.
- Ни одну платформенную ветку нельзя пропускать лишь потому, что «выглядит достаточно длинно» или «слово от автора, наверное, примерно в норме»; число знаков основного текста и «слова от автора» обязано быть реально измерено скриптом и записано в поле журнала.
- При срабатывании этого Skill `общий-очистка-мастер-черновика` и `общий-адаптация-под-платформы` — оба обязательные узлы; пропускать нельзя.
- Определение главы должно быть совместимо с двумя режимами «вход по пути» и «вход по части/тому/главе»; вход по части/тому/главе по умолчанию определяется в `小说正文/`.
- Набор платформ по умолчанию обязательно динамически читать из раздела `平台POV基线表` в `Agents.md` в корне проекта, нельзя жёстко прописывать фиксированный список платформ в исполнителе; если `Agents.md` или в нём раздел `平台POV基线表` отсутствует, обязательно предложить пользователю создать и остановиться, продолжать выполнение нельзя.
- Борьба с водой и проверка бессмысленных знаков — жёсткий гейт; при любой аномалии обязательно вернуть на доработку, нельзя пропускать под предлогом «сходство уже прошло».
- Условие остановки процесса должно выполняться: все указанные платформы сохранены в файл + все гейты пройдены + журнал, позволяющий продолжить, полон.
- Полнота вызовов — жёсткий гейт: `requiredCalledSkills` и `calledSkills` обязаны быть выровнены, и `missingCalledSkills` обязан быть пуст.
- Поля контракта POV — жёсткий гейт: из журнала должно быть прямо видно, «какой комплект POV эта платформа сейчас должна использовать, откуда унаследован, разрешено ли переключение»; если ответить нельзя, считается невосстановимым и непропускаемым.
- Загрязнение шаблонными предложениями — жёсткий гейт: при появлении групп предложений «абстрактное самоповествование + шаблон глагола + канцелярское существительное» или семейства загрязняющих фраз обязательно признавать провалом и возвращать на доработку; нельзя оставлять как средство «стилевой дифференциации».
- Дисциплина использования токенов — жёсткий гейт: запрещено пакетным переписыванием основного текста скриптами «экономить вызовы» или «обходить лимиты»; такое поведение сразу записывается как нарушение, в сводку завершения входить нельзя.

## Проверка завершения

- Прочитаны ли 3 файла references
- Создана ли очередь задач для одной / многих глав
- Завершено ли до платформенной рассылки суждение о выполнимости по знакам и заранее записан ли `blocked_word_count_insufficient` для недостаточных платформ
- Ведётся ли журнал по каждой главе и записаны ли платформенные гейты
- Явно ли запущен `scripts/platform_validate.ps1` для каждого платформенного узла и записаны ли результаты гейтов основного текста / «слова от автора» в журнал
- Зафиксирован ли `platformPovContract` для каждой платформы и подтверждены ли источник наследования или причина одобренного переключения
- Выполнен ли гейт POV для каждого платформенного узла (или ручная перепроверка для глав с переключением взгляда) и записан ли результат в журнал
- Завершена ли поязыковая финальная проверка сходства
- Завершён ли гейт сходства `< 0.20` по схеме «китайские платформы попарно + китайские к исходной главе, английские платформы попарно»
- Выполнен ли гейт качества по борьбе с водой и бессмысленным знакам и возвращено ли на доработку при провале
- Подтверждено ли, что каждая глава каждой платформы — независимый файл `.md` и содержит лишь заголовок, основной текст и `## 作者有话说`
- Выведен ли аудит вызовов: `requiredCalledSkills`, `calledSkills`, `missingCalledSkills`
- Подтверждено ли, что `missingCalledSkills` пуст (иначе объявлять завершение нельзя)
- Выведена ли только сводка без утечки основного текста
- Подтверждено ли, что в платформенных текстах нет семейства загрязняющих фраз (таких как «对照项落在», «先把同一句话拆碎», «先把顺滑的解释拆开», «只求能追溯/复核/对得上»)
- Подтверждено ли отсутствие несанкционированного дрейфа POV по типу «в предыдущих главах третье лицо, в последующих вдруг первое»
- Если при выполнении ИИ оказался недоступен, прервано ли это по `blocked_ai_unavailable` и записано ли руководство по восстановлению (а не сгенерировано ли скриптом в качестве запасного варианта)
