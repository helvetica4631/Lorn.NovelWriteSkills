## Правила автообнаружения шаблонов стиля / образца / писательских исследований

Если в корневом каталоге обслуживаемого проекта есть `Agents.md`, перед сборкой пакета материалов для подачи необходимо:

1. Прочитать `Agents.md` в корне проекта; если там объявлена `主输出平台`, при поиске трёх видов шаблонов в первую очередь подбирать шаблоны, у которых «适用平台» совпадает с основной платформой вывода, при отсутствии совпадений откатываться к шаблонам того же вида с «适用平台：默认»
2. Если в `Agents.md` зарегистрирован «шаблон исследования письма» — прочитать файл шаблона по соответствующему пути и использовать его как базовую линию критериев подачи на целевую платформу и полноты материалов
3. Если в `Agents.md` зарегистрирован «шаблон стиля автора» — прочитать файл шаблона по соответствующему пути и использовать его как справку для единства тона аннотации, образцов глав и материалов
4. Если в `Agents.md` зарегистрирован «шаблон образца произведения» — прочитать файл шаблона по соответствующему пути и использовать его как справку для краткого изложения общего плана, выбора образцов глав, структурных изюминок и пояснения хуков
5. Этот Skill использует только поля, связанные со сборкой пакета материалов для подачи; во внешних материалах нельзя прямо записывать внутреннюю диагностику шаблона, оценки или авторскую самооценку
6. Если в корне проекта нет `Agents.md` или в нём не зарегистрированы соответствующие шаблоны — откат к общему режиму по умолчанию, без ошибок и без блокировки

Поля, потребляемые этим Skill по умолчанию:

- Шаблон исследования письма: критерии подачи на платформу, перечень материалов, требования к аннотации, ограничения-табу
- Шаблон стиля автора: общий стиль, список табу, единство голоса образцов глав
- Шаблон образца произведения: общая повествовательная стратегия, режимы начала глав, интервалы наград, ротация хуков, структурные изюминки

## Правила автоматического обнаружения основной выходной платформы

Если в корневом каталоге обслуживаемого проекта есть `Agents.md` и в нём объявлена `主输出平台`, перед сборкой пакета материалов для подачи необходимо:

1. Прочитать `Agents.md` в корне проекта, взять объявленную в нём `主输出平台` как целевую платформу подачи
2. По соглашению об именовании загрузить соответствующий Skill `общий-вывод-{платформа}`, получить критерии подачи этой платформы, перечень материалов и стандарты арбитража
3. Если в корне проекта нет `Agents.md` или основная платформа не объявлена — пользователь должен явно указать целевую платформу, нельзя по умолчанию действовать по правилам какой-либо конкретной платформы

## Красные линии пакета для редактора (обязательно)

- **Во внешних материалах запрещены любые предложения-самооценки, самовосхваления, самоподтверждения или суждения вместо редактора.**
- Запрещено записывать в `内投版简介` (аннотация для внутренней подачи), `内投版正文` (основной текст для внутренней подачи), `内投版总大纲` (общий план для внутренней подачи), `内投版第 1 卷卷纲` (план 1-го тома для внутренней подачи), внешние сводные экспортируемые файлы нечто вроде: `当前最强一环` («текущее сильнейшее звено»), `当前最弱一环` («текущее слабейшее звено»), `当前残留风险` («текущие остаточные риски»), `当前结论` («текущий вывод»), `可以直接进入编辑内投` («можно прямо подавать редактору»), `编辑会继续看` («редактор продолжит читать»), `适合编辑快扫` («подходит для быстрого просмотра редактором»), `建议现在投稿 / 内投` («рекомендуется подавать сейчас») и подобное.
- Платформенная оценка подписания, вероятностные суждения, вето одним голосом, анализ сильнейшего и слабейшего, авторская самозащита могут существовать лишь в **отдельной задаче оценки** или в **авторских внутренних файлах сверки** и не должны включаться ни в какие внешние материалы.
- «Усвоить имеющуюся оценку / выводы рецензии» означает: исправить проблемы, сделать обещания реальными, дополнить материалы; **а не переписать выводы оценки дословно в материалы для подачи.**
- Если нужна авторская внутренняя сверка, она обязательно должна быть явно помечена «авторский внутренний файл / не отправляется вместе с рукописью»; её нельзя включать в `99_汇总导出件.md` (сводный экспортный файл), нельзя выдавать за пояснительную записку для редактора.

## Требования к соответствию целевой платформы и шаблона общего плана (обязательно)

- Целевая платформа подачи определяется `主输出平台` в `Agents.md` в корне проекта либо явным указанием пользователя.
- Когда у целевой платформы есть особые требования к шаблону общего плана, перед сборкой пакета необходимо сначала прочитать в общем плане `## 模板组合声明` (объявление комбинации шаблонов) / пояснение по использованию шаблона.
- Если объявление шаблона отсутствует и у целевой платформы есть известная система шаблонов, основной шаблон нужно вывести обратным ходом из соответствующего Skill `общий-вывод-*` платформы или её исследования письма.
- При сборке признаётся только `1` основной шаблон + `0–2` вспомогательных. Если в плане параллельно указаны несколько основных шаблонов, это признаётся неудачным объявлением шаблона, сначала нужно исправить.
- **План в материалах для подачи обязательно должен писаться строго по структурным полям и требованиям формата выбранного основного шаблона** (жёстко обязательно); если шаблон объявлен, но план написан не по формату шаблона, такой план считается отсутствующим и не допускается к формальному процессу сборки.
- Если объявление шаблона отсутствует, но материалы в целом самосогласованы, сборку можно продолжать, но по умолчанию выдавать только «предварительную версию пригодного пакета / версию на доработку».
- Если объявление шаблона отсутствует и структура настолько запутана, что нельзя доказать обещание первого тома, долгосрочное питание и точки приземления главной торговой точки, формальную сборку остановить, сначала вернуться в `общий-проектирование-общего-плана` и поправить план.
- Если целевая платформа — Qidian (起点中文网), как специальный арбитражный стандарт этой платформы загружается `references/起点内投材料四件套与裁判标准.md`.

## Предварительный барьер соответствия шаблону (обязательный порядок исполнения)

- **Проверка соответствия шаблону должна происходить до написания любого общего плана / плана 1-го тома для внутренней подачи**, нельзя дописать план, а потом задним числом добавить фразу «каков основной шаблон».
- Проверка соответствия шаблону должна сначала дать как минимум `4` суждения:
	1. Каков текущий основной шаблон;
	2. Каковы вспомогательные шаблоны, не вышли ли они за рамки;
	3. Может ли имеющийся общий план / тома уже поддержать переписывание по полям основного шаблона;
	4. Может ли текущий пакет перейти в «формальную версию для подачи» или должен быть понижен до «предварительной версии пригодного пакета / версии на доработку».
- Если любое из этих `4` суждений не может быть установлено, необходимо сначала остановиться на этапе «вывод о соответствии шаблону», **не выводить прямо формальный внутренний план для подачи**.
- При написании плана обязательно сохранять иерархию полей и привычки именования основного шаблона; можно делать жанровый перевод, но нельзя переписывать основной шаблон в общий стиль резюме.
- Если основной шаблон требует «персонаж героя + матрица подземелий / дел-единиц», то обязательно по пунктам сдавать эти поля; если основной шаблон требует «девять линий / линия X / линия C / матрица дел-единиц», то обязательно по пунктам сдавать соответствующие поля; **нельзя заменять поля основного шаблона самодельной структурой**.

### Доказательство выравнивания полей шаблона (новый жёсткий барьер)

- Недостаточно «знать, как называется основной шаблон»; **обязательно прочитать исходный файл основного шаблона и выделить перечень обязательных к сдаче полей первого / второго уровня этого шаблона**.
- Перед началом написания внутреннего плана обязательно сначала создать `模板字段覆盖表` (таблица покрытия полей шаблона), содержащую как минимум три столбца: `исходное поле основного шаблона`, `соответствующее место в текущем внутреннем плане`, `покрыто ли (да / нет)`.
- `模板字段覆盖表` можно вести как промежуточную проверку в чате либо записать в область плана внутреннего файла; но независимо от сохранения в файл, **эту таблицу обязательно нужно завершить, прежде чем переходить к написанию формального плана**.
- Если поле основного шаблона в общем плане / плане 1-го тома для внутренней подачи лишь «упомянуто концептуально», но не раскрыто по существу структурным содержанием, как требует это поле, оно по-прежнему считается «не покрытым». Например: основной шаблон требует `персонаж героя -> характер / внешность / биография / способности / «милота» / золотой палец`, а написан лишь один абзац-резюме «герой и основной механизм» — это по-прежнему пропуск; точно так же, если основной шаблон требует `матрицу подземелий / дел-единиц`, а последующие тома записаны лишь как «каждый том — одна фраза», «каждый том — одно подземелье» или подобный лозунговый перечень, это тоже считается пропуском.
- Если в `模板字段覆盖表` любое обязательное к сдаче поле «нет», то:
	- нельзя выводить «формальную версию для подачи»;
	- нельзя заявлять, что «общий план / план 1-го тома для внутренней подачи завершены»;
	- сначала необходимо переписать план, затем заново провести проверку покрытия полей.
- Запрещено после написания плана по субъективному суждению говорить «кажется, почти всё покрыто»; **обязательно по полям заново смотреть исходный шаблон и сверять по полям.**

### Барьер читаемости истории плана (новый жёсткий барьер)

- Прохождение покрытия полей шаблона **не означает, что история рассказана ясно**. В `内投版总大纲` и `内投版第 1 卷卷纲` во всех частях, касающихся сюжета, сначала нужно дать редактору понять, «что вообще это за история», и только потом говорить о торговых точках, структуре и питании.
- Во всех пунктах уровня общего плана, касающихся `M0 / X / C / продвижения по томам / матрицы дел-единиц / граней истории (故事面) / этапных узлов`, сначала должен быть абзац `краткого изложения истории` простым человеческим языком: ясно написать, `кто` в `какое время / в какой сцене` из-за `какой цели / какого давления` делает `что`, сталкивается с `каким сопротивлением`, как дело `нарастает / меняет направление`, и оставляет `какие проверяемые последствия / новый пробел`.
- В пунктах уровня плана тома, касающихся историй уровня тома, продвижения групп глав, ключевых глав или ключевых подземелий, нужно как минимум дать редактору понять: `о какой истории рассказывает этот том / эти несколько глав`. Рекомендуемое минимальное развёртывание: `краткое изложение истории`, `сцена (WHEN / WHERE / WHO)`, `основной конфликт`, `ключевые действия / повороты`, `прямые последствия / интрига-хук`.
- Графы вроде `фон / цель / препятствие / задействованные персонажи / скрытая линия завязок / точки переворота` допустимы лишь как дополнение и не заменяют `краткое изложение истории`. **Ясные элементы не равны ясной истории**; если читатель всё ещё не может сказать, «что произошло», считается, что барьер не пройден.
- Для проектов с плотными подземельями / делами-единицами `цель уровня тома + матрица дел-единиц + точки питания по этапам` тоже должны строиться на предпосылке «каждое основное дело-единица сначала ясно говорит, что происходит»; одни названия дел, названия функций, метки питания не считаются завершением.
- Если произведение построено по структуре дел-единиц / подземелий / связанных дел, **каждое названное основное дело-единица в общем плане и плане `1`-го тома не должно сводиться к названию**. Увидев название дела, редактор не узнаёт автоматически, о чём оно; нужно как минимум дополнить: `о чём это дело`, `как герой вмешивается`, `каково основное сопротивление / ошибочное суждение`, `какой результат / пробел для передачи эстафеты приносит это дело`.
- Для проектов с делами-единицами минимальный проходной стандарт `матрицы дел-единиц` — не «перечислить названия дел», а «дать редактору понять примерную историю и роль каждого дела». Если остаются только `название дела + функциональное слово`, считается отпиской-пропуском.
- Если ключевые узлы общего плана / плана тома нельзя по возможности записать как `кто что сделал → какой возвращаемый предмет / изменение состояния оставил → какие проверяемые последствия / пробел следующего шага вызвал`, такой узел по-прежнему остаётся на концептуальном уровне.

## Требования к исполнению полной сборки (обязательно)

- Пакет для подачи — это не «втиснуть материалы в один Markdown-файл», а быстро ответить за редактора как минимум на `5` вопросов:
	1. Что это за книга, можно ли быстро классифицировать;
	2. Заставит ли начало меня читать дальше;
	3. Реализуют ли основной текст и план торговые точки, обещанные аннотацией;
	4. Есть ли у книги долгосрочное питание на `500` тыс. знаков и более и обещание первого тома;
	5. Способен ли автор стабильно дописать её до конца.
- Если цель — Qidian или другая сильная платформа серийной публикации, перед сборкой необходимо сначала пройти внутренний экспресс-контроль: `30 секунд на классификацию`, `3 минуты на продолжение чтения`, `30 тыс. знаков / стоит ли продолжать оценку первого тома`.
- Если цель — внутренняя подача на Qidian, этот репозиторий больше не использует прежнюю минимальную линию подачи «`6000` знаков основного текста + `300` знаков плана» и больше не считает «одиночный план в `2000` знаков» планом по умолчанию; всё исполняется как **версионируемый многофайловый пакет для подачи**.
- Четыре внешних сдаваемых файла для внутренней подачи на Qidian включают как минимум: `内投版简介`, `内投版正文` (не менее 30000 знаков непрерывного основного текста), `内投版总大纲` (минимум 5000 знаков), `内投版第 1 卷卷纲` (минимум 5000 знаков); `组包自检` (самопроверка сборки) допускается сохранять только как авторский внутренний файл сверки той же версии, в число внешних сдаваемых файлов не засчитывается.
- При отсутствии любого внешнего сдаваемого файла нельзя считать, что линия подачи достигнута; даже если файлы полны, но соответствие шаблону, эффективность парадной двери, долгосрочное питание или готовность к исполнению не проходят порог, пакет можно лишь понизить до «предварительной версии пригодного пакета», нельзя прямо присваивать «формальную версию для подачи».
- **Общий план для внутренней подачи обязан охватывать скелет всей книги, а план 1-го тома должен быть отдельным файлом**: ответственные редакторы Qidian, собранные в официальной зоне авторов Yuewen, прямо называют «писать только первый том, последующие тома — позже» активной причиной потери баллов. Подписание у редактора Qidian по существу — это ставка на длинную серийную публикацию на `500` тыс. знаков и более; если общий план не охватывает всю книгу, редактор не может судить, «живы ли последующие тома по-настоящему», и желание подписать прямо снижается. Последующие тома не обязательно расписывать по главам, но каждый том должен **сначала простым человеческим языком рассказать этапную историю**, а затем писать основной конфликт, цель продвижения и этапные торговые точки, нельзя оставлять пустыми или писать «будет определено»; план `1`-го тома, в свою очередь, детализирует обещание первого тома, ритм парадной двери и передачу эстафеты в конце тома до исполнимого уровня.
- Если исходный общий план строится на плотных делах-единицах (например, много томов, много дел, и каждое дело несёт функцию этапного питания), то `内投版总大纲` обязан также явно доказать, что «плотность питания внутри тома» по-прежнему существует, а не сжимать массу дел-единиц в небольшое число лозунгов. По последующим томам редактор должен увидеть как минимум: какой класс основного конфликта решает том, какие основные дела-единицы / типы дел питают внутри тома, о чём каждое из этих дел, какие арсеналы / персонажей / систему / награды по основной загадке питает каждое, а также более дорогой пробел в конце тома, ведущий читателя в следующий том. Если остаются только «название тома + одна фраза продвижения + одна точечная награда», считается недостаточным доказательством долгой линии.
- Если в материалах есть отчёт платформенной оценки подписания, отчёты рецензий глав / персонажей / настроек / томов / общего плана, их необходимо сначала усвоить, а затем решать, можно ли формально собирать пакет; нельзя игнорировать выводы вышестоящих уровней и прямо упаковывать рискованную рукопись как «пригодную версию», а также нельзя переносить дословно текст этих выводов во внешние сдаваемые файлы.
- Если название, аннотация, образцы глав, план, персонажи, настройки противоречат друг другу в обещаниях, необходимо сначала унифицировать жанровое обещание; до унификации можно выводить только «предварительную версию пригодного пакета», нельзя выдавать за формальную версию для подачи.

## Дополнение: экспресс-контроль материалов начала (новое)

- При сборке по умолчанию проверять, поставлены ли в первых `300` знаках образца главы рычаг персонажа и первое давление, образуют ли первые три главы хотя бы один полный цикл хук / накопление / награда или нарастание.
- Если образец главы продвигается в основном пояснением настроек, абстрактными суждениями или авторскими рассуждениями, а не действием, чувствами, выбором и последствиями, по умолчанию относить к риску неэффективной парадной двери.
- Если у героя нет реальных недостатков, прагматичной мотивации и видимого пространства роста, то, даже если настройки, жанр или концепция неплохи, нельзя упаковывать пункт о персонажах как торговую точку высокой зрелости.
- Если основной текст явно не подходит для чтения на телефоне (большие глыбы текста, равномерные группы предложений, медленный первый экран), по умолчанию понижать пункты пригодности образца главы к подаче и эффективности парадной двери.

### Доказательство структуры парадной двери (новое)

- При сборке по стандарту Qidian, помимо четырёх внешних сдаваемых файлов, при авторской внутренней сверке по умолчанию дополнительно готовится «доказательство структуры парадной двери»:
	1. Хук-обязанность, которую несут `0–300` знаков;
	2. Обязанность цели / сопротивления, которую несут `300–800` знаков;
	3. Обязанность первой награды, которую несут `800–1500` знаков;
	4. Обязанность движущей силы следующей главы, которую несёт конец первой главы.
- Это доказательство служит опорой для суждения «30 секунд на классификацию + 3 минуты на продолжение чтения», в качестве внешнего сдаваемого файла не отправляется.
- Если нельзя дать доказательство этих четырёх обязанностей, по умолчанию нельзя признавать «парадную дверь действенной», пакет для подачи следует понизить до предварительной версии или версии на доработку.

## Единое дополнение транзакционного слоя (новое)

- Если основная торговая точка произведения опирается на эмоциональную ценность, напряжение отношений, реализацию роста, переворот идентичности или положение персонажа, при сборке необходимо, чтобы хотя бы один из этих пунктов непрерывно проявлялся в названии, аннотации, начале образца главы; нельзя, чтобы три материала говорили каждый своё.
- Если редактор за `30` секунд всё ещё не видит жанровую классификацию, нынешнюю дилемму героя и причину читать дальше, по умолчанию можно лишь понизить до предварительной версии или версии на предварительную правку.
- При сборке нельзя просто упаковывать «концепция состоятельна» как «высокая зрелость для подачи»; одновременно нужно ответить на три вопроса: за персонажем можно следовать, парадная дверь действенна, долгосрочное питание возможно.

## Требования к усвоению сигналов рецензии (обязательно)

- Пока соответствующие материалы существуют, при сборке по умолчанию в первую очередь усваивать выводы следующих способностей:
	- `общий-оценка-подписания-на-платформе`
	- `общий-рецензия-текста-главы`
	- `общий-рецензия-биографии-персонажей`
	- `общий-рецензия-настроек-истории`
	- `общий-рецензия-плана-тома`
	- `общий-рецензия-общего-плана`
- Если эти выводы есть, их необходимо перевести в действия сборки, а не просто «принять к сведению» в чате:
	- **Остановить формальную сборку**: при наличии фатальных проблем сначала вернуть на доработку;
	- **Понизить до предварительной версии**: материалы ещё не проходят порог, но стоит продолжать дополнять;
	- **Разрешить формальную сборку**: парадная дверь, персонаж, механизм, долгая линия, исполнение — всё достигло порога пригодности для подачи.
- Если готовых отчётов рецензии нет, но материалы явно обнаруживают жёсткие недостатки, соответствующие этим объектам, также необходимо обработать по той же строгой планке, нельзя уходить от суждения под предлогом «ещё формально не рецензировалось».

## Порядок выполнения по умолчанию

1. Сначала определить целевую платформу / канал и стандарты материалов; если платформа не указана, по умолчанию действовать по Qidian (起点中文网).
2. Затем провести инвентаризацию имеющихся материалов, пробелов и наличия повторно используемых выводов оценки / рецензии.
3. Если цель — Qidian (включая подразумеваемый по умолчанию стандарт Qidian при неуказанной платформе), сначала прочитать в общем плане `模板组合声明`; если нет, вернуться к `总纲模板/README.md` и вывести основной шаблон обратным ходом, а при отсутствии более подходящего шаблона выполнить откат по умолчанию на `九线写作总纲.md`.
4. Сначала провести первичную проверку соответствия плана шаблону: разумен ли основной шаблон, не вышли ли вспомогательные шаблоны за рамки, вошли ли ключевые поля в общий план и материалы для подачи.
5. Прочитать исходный файл основного шаблона, выделить обязательные поля, сначала создать `模板字段覆盖表`.
6. **Сначала дать вывод о соответствии шаблону**: можно формально переходить к написанию плана / можно выводить только предварительную версию / сначала обязательно вернуть на доработку общий план.
7. Затем проверить «барьер читаемости истории плана»: во всех пунктах общего плана / плана тома, касающихся сюжета, сначала смотреть, можно ли рассказать понятную историю; если можно лишь перечислить элементы, ярлыки или графы, нельзя продолжать присваивать громкое название «формальной версии».
8. Затем провести барьер качества перед сборкой: остановить формальную сборку / делать только предварительную версию / можно формально собирать.
9. Если основной шаблон — плотные дела-единицы, сначала выделить из исходного общего плана матрицу дел-единиц уровня тома и точки питания по этапам, а затем писать `内投版总大纲`; запрещено временно обобщать последующие тома лишь по названиям томов и ключевым словам финала.
10. Затем собирать в порядке «сначала зацепить взгляд, потом убедить, потом доказать, что умеет писать, в конце указать риски».
11. Если цель — пакет для внутренней подачи фиксированной спецификации, внешние сдаваемые файлы организовать по порядку «`内投版简介` → `内投版正文` → `内投版总大纲` → `内投版第 1 卷卷纲`»; `组包自检` можно хранить только как авторский внутренний файл сверки отдельно.
12. После написания плана обязательно использовать ту же `模板字段覆盖表` для обратной проверки и дополнительно провести «обратную проверку читаемости истории»; если по-прежнему есть пропуски или история всё ещё не ясна, немедленно понизить и вернуть на доработку.
13. Затем провести экспресс-контроль внутри пакета: состоятельны ли 30 секунд на классификацию, 3 минуты на продолжение чтения, основания для оценки 30 тыс. знаков / первого тома.
14. По правилам каталога версий по умолчанию записать обратно в `投稿材料/`, синхронно вести индекс текущей версии, различать «внешние сдаваемые файлы» и «авторские внутренние файлы сверки», затем дать минимальную квитанцию со стороны чата.
15. В конце вывести подсказку об отсутствующих файлах, порядок дополнения и файлы, которые ещё нужно дописать / вернуть на доработку, не выводя суждений вместо редактора.

## Жёсткие правила

- Запрещено иметь только план, без образцов глав и обещания торговых точек.

- Запрещено при отсутствии ключевых материалов выдавать пакет за полную версию для подачи.
- Когда платформа не указана, по умолчанию действовать по критериям Qidian (起点中文网); запрещено пропускать эти критерии по умолчанию и прямо писать расплывчатые правила платформенной версии.
- В стандарте Qidian запрещено, не прочитав объявление шаблона общего плана, прямо выводить формальный пакет для подачи.
- В стандарте Qidian запрещено **сначала писать общий план / план 1-го тома для внутренней подачи, а потом добавлять пояснение о соответствии шаблону**; барьер шаблона должен предшествовать выводу плана.
- Запрещено параллельно указывать несколько основных шаблонов; при сборке признаётся только `1` основной шаблон + `0–2` вспомогательных.
