# Общий процесс выполнения многоплатформенного вывода и восстановление с контрольной точки (справочно)

Этот документ — сопутствующий справочник к `通用-多平台输出编排/SKILL.md`, он даёт дополнительные подробности выполнения шагов и пояснения принципов. **Авторитетное определение процесса — в SKILL.md** (замкнутый цикл из 15 шагов в пяти этапах A→E), этот документ даёт вспомогательную информацию по темам.

## Нормализация входа

Поддерживаются следующие входы:

- `chapterPath`
- `chapterPaths[]`
- Вставленный основной текст (только если можно определить необходимые метаданные)
- `platforms` (необязательно; если не предоставлено, набор платформ по умолчанию читается из раздела `平台POV基线表` в `Agents.md` в корне проекта; если такого раздела нет, обязательно предложить пользователю создать и остановиться)

## Правила набора платформ по умолчанию

Когда в команде пользователя `platforms` не указаны, набор платформ по умолчанию определяется по следующим правилам:

1. Обязательно прочитать `Agents.md` в корне проекта, найти в нём раздел `平台POV基线表`, и взять перечисленные там платформы как набор платформ вывода по умолчанию на этот раз.
2. Если в корне проекта нет `Agents.md` или в нём нет раздела `平台POV基线表`, обязательно предложить пользователю создать этот раздел и записать в него список целевых платформ, затем **немедленно остановиться**, продолжать выполнение нельзя.
3. Формат `平台POV基线表` (существует отдельным разделом в `Agents.md`): одно название платформы в строке (совпадает с суффиксом имени Skill `通用-输出*版`), строки, начинающиеся с `#`, — комментарии.

## Вывод пути и номера

### Номер главы в первую очередь разбирается из числового префикса имени файла

- Стандартная форма: `{часть.том.глава} заголовок.md`
- `chapterNo`: полный числовой префикс
- `chapterIndex`: последний сегмент номера

Если `chapterNo` разобрать не удаётся — только тогда задавать вопрос.

### Вывод каталога части / тома

- `{分卷目录}` (каталог тома) = имя каталога, где лежит исходный файл
- `{分部目录}` (каталог части) = имя каталога на уровень выше `{分卷目录}`

Если путь не удаётся стабильно вывести, только тогда задавать минимально необходимые вопросы.

## Предпроверка контракта платформенного POV (новое, жёстко)

### Сначала определить форму POV исходника

- При создании очереди задач по главам сначала определить, к какому типу относится каждая исходная глава: устойчивая глава одного взгляда / глава с переключением взгляда / последовательная глава многих точек зрения.
- Если исходная глава изначально является главой с переключением взгляда или последовательной главой многих точек зрения, продолжать подчиняться правилам взгляда `通用-创建小说正文`; слой многоплатформенного вывода не должен самовольно упрощать её до другой POV и не должен без причины превращать главу одного взгляда в главу перехода лица.

### Порядок создания и наследования платформенного контракта

- Каждая платформа обязана создать один `platformPovContract`, содержащий как минимум: `expected`, `lang`, `baselineSource`, `switchPolicy`.
- Приоритет: явное указание пользователя > ранее завершённые главы той же платформы > существующая цепочка POV исходника > первая прошедшая глава этой платформы в этой партии.
- Если в каталоге целевой платформы уже есть предыдущие главы той же книги, той же части / тома, обязательно в первую очередь прочитать последнюю прошедшую главу; при необходимости дополнительно посмотреть последние 2–3 главы, подтвердить стабильность цепочки этой платформы, затем продолжать писать.
- После фиксации платформенного контракта последующие последовательные главы по умолчанию целиком наследуют; нельзя в каждой главе заново решать первое / третье лицо.

### Единственные сценарии, где переключение разрешено

- Исходная глава изначально является главой с переключением взгляда или последовательной главой многих точек зрения, и платформенная версия сохраняет эту структуру;
- Пользователь явно требует для этой платформы переход POV;
- Историческая цепочка платформы уже стабильно использует другую POV, в этот раз лишь продолжение по имеющейся цепочке.

Помимо указанных сценариев любое переключение на новую цепочку лица на полпути записывается как `pov_drift_detected` или `pov_switch_without_approval`.

## Общий порядок выполнения (соответствует пяти этапам A→E в SKILL.md)

| Этап | Диапазон шагов | Пояснение |
| --- | --- | --- |
| A Определение входа | Шаги 1–3 | Разбор путей и нормализация |
| B Диапазон платформ и очередь задач | Шаги 4–6 | Разбор параметров платформ, создание очереди задач, досье POV |
| C Мастер-рукопись и платформенное переписывание | Шаги 7–9 | Очистка мастер-рукописи, платформенная прикидка различий, по очереди вывод версий каждой платформы |
| D Финальная проверка гейтами и возврат на доработку | Шаги 10–14 | Гейты знаков/POV/сходства/качества + возврат на доработку непрошедших платформ |
| E Определение завершения | Шаг 15 | Сводка, аудит, вывод резюме |

## Обязательная стратегия понижения при недоступности ИИ (новое)

- Применимые сценарии: ограничение квоты субагентов, недоступность модели, постоянные сбои вызовов.
- Единственные допустимые действия:
  1) немедленно остановить генерацию основного текста;
  2) записать статус журнала `blocked_ai_unavailable`;
  3) записать точку неудачного вызова, причину неудачи, вход следующего восстановления;
  4) разрешается продолжать только «чтение, гейты, приведение журнала в порядок» и иные действия только для чтения или проверки.
- Явно запрещено: переключаться на любую скриптовую цепочку переписывания для генерации основного текста (включая пакетную замену, склейку шаблонов, автоматическое расширение, правиловое переписывание).
- При попадании в этот сценарий нельзя заявлять «задача завершена», можно выводить только квитанцию блокировки и шаги восстановления.

## Сначала прикидка, потом письмо (жёстко)

- Для каждого узла «глава × платформа» обязательно сначала сформировать платформенный эскиз прикидки, затем переходить к фактическому переписыванию основного текста и сохранению в файл.
- Эскиз прикидки должен ответить как минимум на:
  - какую основную информацию этой главы обязательно сохранить;
  - какой стиль / ритм / хук / тенденция заголовка у этой платформы приоритетны;
  - какие несколько действий по снижению повторов собираемся применить в этот раз;
  - какие выражения ни в коем случае нельзя прямо навязывать из нейтральной основы или исходных фраз исходной главы.
- Эскиз прикидки служит только исполнению, в окончательный файл не попадает, в чате длинно не показывается.
- Без этого шага нельзя прямо переходить к написанию платформенного основного текста; «сначала написать нейтральный текст, затем пакетно слегка править» считается нарушением процесса.

## Единственные сценарии, где допускается прерывание (жёстко)

- Не удаётся разобрать `chapterNo` из имени исходного файла
- Не удаётся стабильно вывести `分部目录 / 分卷目录`
- Пользователь вставил лишь основной текст и необходимые метаданные отсутствуют
- Реальная ошибка исполнения не позволяет продолжить следующий шаг
- Способность генерации ИИ недоступна (лимит субагентов / модель недоступна / сбой вызова)

Кроме указанных сценариев, нельзя приостанавливаться в ожидании ответа пользователя ради «отчёта о прогрессе», «подтверждения предпочтений», «напоминания о следующем шаге».

## Правила параллелизма

### Консервативный верхний предел по умолчанию

- Одновременно продвигать не более **2 задач по главам**
- Внутри каждой главы по умолчанию параллельно не более **2 платформенных ветвей**
- Общее число активных платформенных ветвей в глобальном масштабе по умолчанию не более **4**

### Границы параллелизма

- 5.1 До завершения чтения исходной главы нельзя запускать никакие платформенные ветви
- Внутри платформы обязательно последовательно: прикидка → заголовок → основной текст → сохранение → гейты → возврат на доработку
- Пока любая платформа не прошла гейты, нельзя вырываться вперёд к финальной проверке
- Пока любая глава не завершила все целевые платформы, нельзя объявлять эту главу завершённой

### Стратегия «скользящего» продвижения по многим главам

- Для задач с многими главами обязательно сначала выполнить разовую предпроверку: существование пути, разбор номера, вывод каталога, нормализация набора платформ.
- Если среди многих глав есть жёсткая нехватка параметров, обязательно сначала разом свести недостающие пункты, затем спрашивать; запрещено возвращаться с вопросами по главам.
- После создания очереди задач по умолчанию продвигаться «скользящим» образом по порядку входа; если пользователь явно не требует, нельзя самовольно переставлять порядок глав.
- Общие настройки одного тома, формулировки платформенных гейтов, шаблон журнала и шаблон резюме можно использовать повторно, но каждая глава обязана независимо выделять основную информацию и независимо проходить финальную проверку.
- **Гейт полного замкнутого цикла по главам**: при оркестровке многих глав каждая глава всё равно обязана независимо и полностью выполнить все подшаги 15-шагового замкнутого цикла. Следующие действия считаются нарушениями:
  - Прямо покрывать шаг 7 (очистка) многих глав выводами прикидки одной очищенной мастер-рукописи — каждая глава обязана независимо вызывать 通用-提纯多平台母稿
  - Считать матрицей адаптации одного набора шаг 8 (адаптация) всех глав — каждая глава обязана независимо вызывать 通用-多平台小说适配
  - После разового сохранения многоплатформенных версий многих глав заявлять «гейты пройдены» — после сохранения каждая глава обязана независимо выполнить все гейты шагов 10–14
  - Делать финальную проверку сходства для многих глав лишь один раз — каждая глава обязана независимо выполнить поязыковую финальную проверку сходства шага 11
- Провал одной главы не должен загрязнять уже прошедшие узлы других глав; изоляция провалов должна проводиться по границам главы.

## Механизм журнала

### Каталог журнала

- `SOP执行日志/多平台输出/`

### logKey одной главы

- `chapterPath + platforms (нормализованная сортировка)`

### logKey для многих глав и вставленного основного текста

- Многие главы: `normalized(chapterPaths, склеенные после удаления дублей в порядке входа) + platforms (нормализованная сортировка)`
- Вставленный основной текст: `source=inline + chapterNo + 分部目录 + 分卷目录 + platforms (нормализованная сортировка)`

### Правила продолжения

- Найти последний журнал со `status != completed` и тем же `logKey`
- Если есть: продолжить запись и восстановить с контрольной точки
- Если нет: создать новый журнал

### Минимальные поля журнала

- `sop`
- `executionId`
- `logKey`
- `status`
- `startedAt / updatedAt`
- `inputs`
- `derived`
- `sourcePovPlan`
- `platformPovContracts`
- `checkpoint`
- `outputs`
- `similarityCheck`
- `platformValidate`
- `povCheck`
- `errors[]`

### Рекомендуемые поля партии и главы

- Верхний уровень `derived` содержит как минимум: `chapterCount`, `currentChapterNo`, `currentPlatform`
- Верхний уровень `checkpoint` содержит как минимум: `phase`, `nextAction`
- Верхний уровень должен напрямую отвечать на вопрос «откуда берётся нынешний контракт POV платформы, разрешено ли переключение», как минимум сохранять `sourcePovPlan` и `platformPovContracts`
- В режиме многих глав рекомендуется использовать `chapters[]` для несения состояния каждой главы, каждая запись главы содержит как минимум:
  - `sourcePath|sourceLabel`
  - `derived.chapterNo / chapterIndex / 分部目录 / 分卷目录`
  - `sourcePovPlan / platformPovContract`
  - `checkpoint`
  - `status`
  - `outputs`
  - `platformValidate`
  - `povCheck`
  - `textQuality`
  - `similarityCheck`

### Правила повторного использования завершённых узлов

- При продолжении любой узел «глава × платформа», у которого уже `written=true`, поля гейтов полны и статус «пройдено», обязательно пропускать напрямую.
- При продолжении нельзя перезаписывать уже зафиксированные `platformPovContracts`; если суждение этого раза конфликтует со старым контрактом, обязательно сначала перепроверить источник, потом решать, одобрять ли переключение, а не прямо менять контракт.
- Перезапускать уже записанный узел допускается только в следующих случаях:
  - финальная проверка этой главы явно требует возврата на доработку;
  - поля журнала неполны, невозможно подтвердить, действительно ли он прошёл;
  - пользователь явно требует полностью переписать этот узел.

### Правила слияния при параллельной записи журнала

- Если параллельно продвигается несколько платформенных ветвей, перед любой записью журнала обязательно сначала прочитать последнюю версию, затем слить поля, за которые отвечает эта ветвь, и записать целиком с перезаписью.
- Запрещено слепо писать по старой копии, затирая `outputs / gates / checkpoint / errors / nextAction` других платформ.

### Правила для многих глав

- Для каждой главы свой подчинённый журнал
- Дополнительно можно вести один главный журнал партии
- Запрещено одним смешанным журналом нести мелкозернистое платформенное состояние многих глав

## Определение завершения главы и партии

- Одна глава: можно записать `completed` лишь после того, как все целевые платформы записаны и прошли гейты, проверку согласованности POV, сканирование качества текста, проверку согласованности стиля и поязыковую финальную проверку сходства.
- Много глав: только когда каждая глава независимо завершила указанную финальную проверку, статус верхнего уровня партии можно записывать как `completed`.
- Если есть главы с провалом или заблокированные главы, статус верхнего уровня обязательно сохраняет `failed` или `blocked_missing_input`, а провалившиеся узлы и следующие действия записываются в журнал.
