# Нормы резюме и журнала многоплатформенного вывода

## Когда обновлять журнал

Дописывать в один и тот же файл журнала как минимум в следующие моменты:

1. После завершения разбора входа и вывода пути
2. После завершения чтения исходной главы
3. После завершения прикидки каждой платформы
4. После успешного сохранения в файл каждой платформы
5. После каждого возврата на доработку
6. После завершения сводки платформенных гейтов
7. После завершения проверки POV
8. После завершения сканирования качества текста
9. После завершения финальной проверки сходства
10. Перед выводом резюме поставить `status=completed`

## Структура полей журнала (жёсткий минимум)

Журнал должен напрямую поддерживать восстановление с контрольной точки, как минимум охватывать следующие уровни:

- Верхний уровень: `sop`, `executionId`, `logKey`, `status`, `startedAt`, `updatedAt`, `inputs`, `derived`, `sourcePovPlan`, `platformPovContracts`, `checkpoint`, `errors[]`
- Режим одной главы: на верхнем уровне можно прямо нести `outputs`, `platformValidate`, `povCheck`, `textQuality`, `similarityCheck`
- Режим многих глав: обязательно поддерживать `chapters[]`, запись каждой главы должна независимо нести:
  - `derived.chapterNo / chapterIndex / 分部目录 / 分卷目录`
  - `sourcePovPlan / platformPovContract`
  - `checkpoint.phase / nextAction`
  - `status`
  - `outputs`
  - `platformValidate`
  - `povCheck`
  - `textQuality`
  - `similarityCheck`

## Минимальные поля записи платформенного вывода

Каждая запись вывода «глава × платформа» должна содержать как минимум:

- `title`
- `outputPath`
- `written`
- `notes`
- `attempt`
- `povExpected`
- `gates`

## Формулировка полей gates (должны позволять восстановление)

`gates` как минимум должны поддерживать следующие подобъекты; подпункты не затронутых платформ могут быть пустыми, но формулировка полей должна быть единой:

- `countChapter`: `{ reportPath, meetsAll, len, cjk, minLen, minCJK, maxCJK }`
- `countAfterword`: `{ reportPath, hasAfterword, afterwordCJK, minAfterwordCJK, maxAfterwordCJK }`
- `countAfterwordWords`: `{ reportPath, hasAfterword, wordCount, minWords, maxWords }`
- `noCjkExceptMarker`: `{ reportPath, pass }`
- `padLike`: `{ reportPath, pad_like_sentences_before, pad_like_sentences_after, pad_like_lines_before, pad_like_lines_after, forced_kept_due_to_min, removed_pad_sentences }`
- `povConformance`: `{ reportPath, expected, lang, pass, counts, reasons, baselineSource, inheritedFrom, switchApproved, switchReason }`
- `textQuality`: `{ reportPath, flagsCount, filesFlagged }`
- `styleConformance`: `{ pass, checks, notes }`

При этом:

- Для китайских платформ обязательно в первую очередь записывать `countChapter`, `countAfterword`, `padLike`
- Для английских платформ обязательно в первую очередь записывать `countChapter`, `countAfterwordWords`, `noCjkExceptMarker`
- Все платформы должны поддерживать `povConformance`, `textQuality` и `styleConformance`

## Рекомендации по написанию checkpoint

- Уровень партии: `batch_manifest_ready`, `chapter:1.2.4:queued`, `chapter:1.2.4:similarity_check:pass`
- Уровень платформы: `chapter:1.2.4:platform:知乎:pov_locked`, `chapter:1.2.4:platform:知乎:written`, `chapter:1.2.4:platform:GoodNovel:gate_failed`, `chapter:1.2.4:platform:GoodNovel:pov_failed`
- `nextAction` обязан чётко писать, что дальше: продолжить какую-то платформу, вернуть на доработку какую-то платформу, дополнить параметры или завершить резюме

## Требования к журналу в режиме многих глав

- В режиме многих глав можно дополнительно вести сводную таблицу партии, но нельзя смешанными полями скрывать мелкозернистое состояние каждой главы.
- Запись каждой главы должна уметь независимо ответить на четыре вопроса:
  1. На каком шаге сейчас остановились;
  2. Какие платформы реально прошли гейты;
  3. Какие платформы провалились или ждут возврата на доработку;
  4. Что делать дальше.

## Ограничения параллельной записи

- Параллельные платформенные ветви перед записью журнала обязаны сначала слить последний журнал, нельзя слепо писать по старой копии.
- Ни одна ветвь не должна перезаписывать уже записанные другими ветвями `attempt`, `gates`, `outputPath`, `errors`, `checkpoint`.

## Правила вывода в диалоге

- Выводить только резюме, не выводить основной текст
- Резюме обязательно группируется по главам (пакетный режим)
- По каждой главе независимо перечислять результат записи, сводку по гейтам и результат поязыковой проверки сходства

## Минимальная структура резюме по одной главе

1. Пути и заголовки платформ, для которых сгенерировано и записано
2. Самопроверка по ограничениям
3. Контроль сходства (китайская группа / английская группа / N/A)

### Минимальные пункты самопроверки по ограничениям

- Пройден ли гейт знаков
- Пройден ли гейт «слова от автора»
- Пройдена ли согласованность взгляда / лица повествования
- Пройдено ли сканирование качества текста
- Пройдена ли согласованность стиля
- Состоятельно ли «информация не потеряна»
- Состоятельно ли «≥ 80% новых формулировок»
- Синхронизирован ли новый заголовок и нет ли совпадения названий
- Содержит ли структура вывода только «основной текст + `## 作者有话说`»- **Соответствие исполнения шагов**: все шаги с заявлением «вызвать skill» загружены через инструмент `skill()` соответствующим Skill (да/нет)
- **Шаги не пропускались самовольно** (да/нет; если были пропуски, написать причину и основание)
## Минимальная структура резюме по многим главам

1. Блок результатов по каждой главе
2. Независимые результаты гейтов и сходства каждой главы
3. Общий обзор партии

### Общий обзор партии содержит как минимум

- Число завершённых глав
- Число глав с провалом / заблокированных глав
- Если есть провал: перечислить `chapterNo + platform + причина + путь отчёта`

## Критерии успеха

- Каждая платформа соблюдает жёсткие ограничения своего Skill платформенного вывода
- Все сгенерированные платформенные файлы прошли гейты
- Все гейты согласованности POV пройдены (или исполнено по одобренному плану переключения)
- Вся поязыковая финальная проверка сходства пройдена
- В чате не утёк основной текст, возвращена только сводка
- В режиме многих глав порядок совпадает с входным
