# Пакетный режим глав и журнал непрерывности

## Цель пакетного режима

Не снижая порога качества одной главы, сократить повторную работу благодаря исполнению по фазам:

- Контекст прогревается один раз, переиспользуется многократно
- Реже переключаться между ролями автора / рецензента / читателя
- Доработка только для глав, не достигших нормы, а не переделка всего пакета заново

## Входные данные пакетного режима

- `CHAPTER_FILES[]`
- `OUTLINE_FILES[]` (необязательно)
- `CHAPTER_BATCH[]`
- `BATCH_ID` (необязательно)

Если задан `CHAPTER_BATCH[]`, ориентироваться на него; если задан только `CHAPTER_FILES[]`, по умолчанию строить таблицу задач по порядку глава за главой и при отсутствии параметров использовать тот же `OUTLINE_FILE` или соответствующий элемент `OUTLINE_FILES[]`.

## Принципы исполнения пакетного режима

1. Сначала полная предварительная проверка путей, нумерации, каталогов и недостающих параметров
2. Построить упорядоченную таблицу задач
3. Исполнять фазовым конвейером
4. Порог по главам, доработка по главам, сводка по главам
5. Изоляция сбоев, не загрязнять другие главы

## Жёсткие ограничения фазового конвейера (жёсткий контроль доступа)

- **Граница пакетного режима — в этом файле**: каждая глава в каждой фазе обязана независимо выполнить все подшаги, охваченные этой фазой, нельзя сокращать, пропускать или объединять.
- **В одном пакете допускается общий прогрев контекста** (например, однократное чтение Agents.md, вывод всех путей), но нельзя делить «статус завершения».
- **Продвигаться необходимо по фазам**, а не прогонять одну главу по всей цепочке и затем переключаться на следующую. Но любая глава до завершения всех подшагов текущей фазы не может досрочно переходить в следующую фазу.
- **Суждение о пороге и доработка выполняются на уровне глав**, нельзя заставлять уже достигшие нормы главы «бежать впустую» и переделываться.
- **Пока есть главы, не завершившие шаг 10 или 11**, весь пакет может быть только `in_progress`.
- **Запрещено перескакивать между фазами**: нельзя пропускать независимую рецензию главы в фазе рецензии на основании того, что «содержание главы на этапе создания уже написано хорошо».

## Рекомендуемый порядок фаз (с ограничениями полноты по главам)

Каждая фаза должна удовлетворять «ограничению полноты по главам» справа:

| Фаза | Охватываемые шаги SKILL.md | Ограничение полноты по главам |
| --- | --- | --- |
| 1. Инициализация пакета | Шаг 0 (однократный вывод путей для всего пакета) | Шаги 0.2 (повторная проверка источников-арбитров) и 0.6 (проверка соответствия путей) каждой главы обязаны выполняться независимо по главам, пропускать нельзя |
| 2. Пакетное создание и добор знаков | Шаги 1→1.5→2 (исполнять по главам) | Каждая глава независимо генерирует контрольную карточку, независимо делает проверку непрерывности перед написанием, независимо создаёт основной текст; контроль числа знаков → цикл расширения по главам прогоняется независимо |
| 3. Пакетная доводка и удаление ИИ-привкуса | Шаги 3→4→5 (исполнять по главам) | Каждая глава независимо загружает 通用-正文润色, 通用-去AI味重写, 通用-润色作者有话说; перезаписывает свои файлы; после удаления привкуса каждая глава независимо, по требованию одиннадцатого шага `通用-去AI味重写`, сохраняет отчёт об удалении ИИ-привкуса этой главы (DESAI_REPORT_FILE), нельзя одним отчётом покрывать несколько глав |
| 4. Пакетная рецензия и доработка | Шаги 6→7→8→9→10 (исполнять по главам) | Каждая глава обязана независимо загрузить 通用-审阅章节正文, независимо использовать полный шаблон отчёта, независимо выполнить двухосевой предварительный фильтр и цикл IF/THEN по оценке; нельзя делить отчёт рецензии |
| 5. Пакетные читательские продукты | Шаги 11→12 (исполнять по главам) | Каждая глава независимо обновляет реестр непрерывности, независимо читает и пишет читательские заметки, независимо пишет рецензию на главу |
| 6. Вывод пакетной сводки | Шаг 13 (сначала свод по главам, затем агрегирование) | Каждая глава сначала завершает поля сводки одной главы, затем сводятся в обзор пакета |

**Нельзя читать только названия отметок, не читая содержимое таблицы.** Ограничение полноты по главам справа так же важно, как название фазы слева, соблюдать нужно оба одновременно.

## Реестр непрерывности

В пакетном режиме рекомендуется вести:

- `CONTINUITY_LEDGER_FILE`

Записывать как минимум:

- Якорь номера главы
- Якорь временной линии
- Изменения состояния персонажей
- Состояние способностей / состояние цены
- Ключевые доказательства
- Невозвращённые хуки
- Объект, наиболее легко остывающий в цепочке текущей главы
- Приоритетный слой обратной записи по текущему суждению

## Каталог журналов и правила возобновления

- При каждом исполнении обязательно создавать или продолжать журнал в `SOP执行日志/撰写章节/`.
- Журнал одной главы использует `logKey = OUTLINE_FILE + CHAPTER_FILE` для сопоставления с последним незавершённым журналом и возобновления.
- В пакетном режиме необходимо одновременно вести:
  - Основной журнал пакета
  - Подчинённый журнал каждой главы
- `batchLogKey` можно получить, склеивая по порядку `OUTLINE_FILE + CHAPTER_FILE` каждой главы пакета.

## Правила журнала

### Подчинённый журнал одной главы

- Один на главу, поддерживает независимое восстановление с контрольной точки
- Содержит как минимум: `sop`, `executionId`, `logKey`, `status`, `startedAt`, `updatedAt`, `inputs`, `derived`, `checkpoint`, `steps`, `artifacts`, `errors[]`
- `checkpoint` отслеживает как минимум: `nextStep`, `phase`, `nextAction`
- `checkpoint` по возможности также отслеживает: `chainStatus` (closed / surface_fixed_only / needs_upstream_rewrite) и `rewriteLevel`
- На шаге 2 нужно записывать `iteration` каждого раунда и `Len/CJK/BodyCJK/MeetsMinCJK/WithinRange/MeetsAll`, а также указывать `statsSource=scripts/count-chapter.ps1`
- На шаге 2 также нужно записывать изоморфные поля «такты/ротация»:
  - `HookType` (интрига / конфликт / аномалия / действие / диалог)
  - `MidPayoff` (одна фраза о награде в середине, на которую можно сослаться по позиции)
  - `TailDriver` (вопрос-эстафета в конце главы)
  - `RotationCheck` (нет ли перегруза повторами относительно двух предыдущих глав: Yes/No)
  - `GatePass` (контроль четырёх тактов: Pass/Fail)
- Нельзя записывать «статистику без пробелов», «NoWhitespaceLen» или любой самодельный подсчёт знаков в поля контроля доступа; если нужно сохранить справочное значение, оно выносится отдельно как `referenceOnly` и не должно использоваться для суждения о достижении нормы
- На шаге 9.5 нужно записывать `iteration` каждого раунда и последнюю оценку как чистое число

### Основной журнал пакета

Записывать как минимум:

- `batchId`
- `items[]`
- `status` каждой главы
- `checkpoint` каждой главы
- `Len/BodyCJK/MeetsMinCJK/WithinRange` каждой главы

> ⚠️ Раньше это поле называлось `Meets3500`, теперь заменено на `MeetsMinCJK`; реально проверяется `MinCJK`, а не жёстко заданное 3500.

- `score` каждой главы
- `consistency` каждой главы
- `chainStatus` каждой главы
- `rewriteLevel` каждой главы
- `HookType / MidPayoff / TailDriver / RotationCheck / GatePass` каждой главы

Для агрегированных показателей пакета рекомендуется одновременно записывать:

- `gatePassRate` (доля глав с GatePass=Pass)
- `rotationOverloadCount` (число глав с RotationCheck=Yes)
- `hookTypeDistribution` (распределение типов хуков)
- `midPayoffCoverage` (доля глав с непустым MidPayoff)
- `tailDriverCoverage` (доля глав с непустым TailDriver)

Каждый элемент `items[]` дополнительно должен содержать как минимум:

- `index`
- `inputs.OUTLINE_FILE / inputs.CHAPTER_FILE / inputs.RELATED_CONTEXT_FILES[]`
- `derived.REVIEW_REPORT_FILE / derived.READER_NOTE_FILE / derived.BOOK_REVIEW_FILE`
- `derived.chapterNo / derived.第X部 / derived.第Y卷` (если выводимо)
- `metrics.BodyCJK / metrics.MeetsMinCJK / metrics.WithinRange / score`

> ⚠️ Раньше это поле называлось `Meets3500`, теперь заменено на `MeetsMinCJK`; реально проверяется `MinCJK`, а не жёстко заданное 3500.

- `metrics.HookType / metrics.RotationCheck / metrics.GatePass`

## Правила предупреждений контроля доступа пакета (новое)

- Если `gatePassRate < 0.90`: весь пакет нельзя признавать `completed`, как минимум один раз войти в структурную доработку.
- Если `rotationOverloadCount >= 2`: контрольная карточка следующего пакета или следующего раунда обязана принудительно сменить тип хука.
- Если `midPayoffCoverage < 1.00`: главы без награды в середине в обязательном порядке дорабатываются в первую очередь.
- Если `tailDriverCoverage < 1.00`: главы без эстафеты в конце главы нельзя пропускать в итоговую рецензию.

## Изоляция сбоев

- Сбой одной главы не должен загрязнять результаты других глав
- Уже запущенные главы можно довести до безопасной точки
- Незапущенные главы можно приостановить, но в сводке это обязательно отметить

## Моменты обязательного сохранения обновлений

1. После завершения шага 0: записать производные пути и `checkpoint.nextStep=1`
2. В начале каждого основного шага: пометить `started`
3. В конце каждого основного шага: записать `ok=true/false` и новый `checkpoint`
4. После каждого расширения и контроля числа знаков на шаге 2: обновить поля статистики
5. Каждый раз на шаге 9.5 при извлечении оценки и решении о доработке: обновить оценку и `nextAction`
6. После завершения шага 4: записать путь отчёта об удалении ИИ-привкуса в `artifacts.DESAI_REPORT_FILE` (обновлять после каждого раунда переписывания основного текста с удалением привкуса)
7. После завершения шага 10 / 11: записать пути читательских заметок / рецензии на главу в `artifacts`
8. Перед выводом итоговой сводки: записать `status` как `completed`
9. Если жёсткая нехватка параметров блокирует работу: записать `status` как `blocked_missing_input` и в `checkpoint.nextAction` чётко указать минимальные недостающие пункты
