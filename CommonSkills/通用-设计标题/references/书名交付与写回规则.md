# Правила поставки и обратной записи названий

## Структура вывода по умолчанию

### A. Пояснение метода (кратко)

- Вокруг какого материнского ядра спроектировано это именование
- Каков самый важный компромисс этого раунда
- Если был старый вариант, в чём основные его проблемы

### B. Таблица заголовков по каждой платформе

По каждой платформе выводить:

- 10 заголовков-кандидатов
- В порядке рекомендации
- К каждому заголовку приложить:
  - 1 фразу с причиной
  - Общий балл Rubric
  - Ключевые пункты бонуса
  - Если заголовок не входит в shortlist — 1 фразу о причине понижения

Дополнительные требования:

- 10 заголовков в формальной таблице кандидатов по умолчанию все должны быть рекомендуемыми, различается лишь сила рекомендации.
- Уже отброшенные внутренние черновики нельзя класть в формальную таблицу кандидатов для количества; если их нужно показать, то только в необязательном разделе разбора.

### C. Главная рекомендация по каждой платформе

Свести как минимум:

- Платформа
- Главная рекомендация
- Суждение одной фразой
- Общий балл
- Основание рейтинга (предельно кратко)
- Пункт отличия от других платформ (предельно кратко)

### D. shortlist (необязательно, но рекомендуется)

Дать как минимум 2 группы:

- shortlist коммерческого клика
- shortlist репутационной фактуры

### E. Сводная таблица Rubric (по умолчанию обязательна)

Вывести как минимум:

- Покомпонентные баллы первых 3 заголовков каждой платформы
- Соответствующий общий балл
- Основание ранжирования одной фразой

### F. Внутренний разбор отсева (необязательно)

Дополнять только в следующих случаях:

- Пользователь явно просит посмотреть отсеянные варианты
- В этом раунде действительно сначала была сгенерирована группа внутренних черновиков, а затем явно проведён отсев

Если этот раздел включён, по каждой платформе максимум пояснять:

- 1–3 внутренних черновика, не вошедших в формальную таблицу кандидатов
- Причину отсева каждого

### G. Самопроверка (включая обязательный контроль доступа дедупликации между платформами)

#### Проверки уровня блокировки — обязаны быть пройдены до записи в файл, при непрохождении поставка запрещена

1. **Глобальная дедупликация между платформами**: свести заголовки-кандидаты всех платформ в один глобальный перечень, сопоставить по пунктам. Если какие-то две платформы используют один и тот же заголовок, обязательно заменить и заново пройти проверку, пока дубликатов не останется. Окончательное число поставляемых заголовков должно равняться числу платформ × числу кандидатов на платформу (m × n взаимно неповторяющихся).
2. **Дедупликация внутри одной платформы**: кандидаты внутри одной платформы не должны повторяться.

#### Обычные проверки — при непрохождении поставлять только после правки

- Похоже ли на название книги, а не на рекламный текст
- Охватывает ли действительную торговую точку произведения
- Нет ли явного совпадения конструкций (даже если не полностью одинаковы, нужно избегать чрезмерно схожих синтаксических структур)
- Адаптировано ли под платформу, а не механически «сменили кожуру»
- Разведены ли основные оси главных рекомендаций разных платформ
- Действительно ли оценка влияет на ранжирование, а не является украшением

## Требования к записи в файл

- Если пользователь явно не просил «сначала набросать только в диалоге, файлы не трогать», результат обязательно записывается в репозиторий.
- Место по умолчанию: `小说简介/《作品名》多平台书名方案_vYYYY-MM-DD-rN.md`
- Если пользователь сейчас редактирует существующий файл варианта названий: по умолчанию обновлять текущий файл; если пользователь явно просит сохранить старую версию, дописать раздел «重做版 / 修订版» («переделанная версия / исправленная версия»).
- Если в репозитории уже есть устоявшийся способ именования, в приоритете сложившаяся практика репозитория.

## Принцип минимальных уточняющих вопросов

Задавать уточняющие вопросы разрешается только если следующую информацию нельзя автоматически вывести из контекста или рабочей области:

1. Делать название всей книги или названия частей / томов
2. Нужна ли многоплатформенная версия
3. Выводить в рабочую область или только набросать в чате

Кроме этого, по умолчанию сразу приступать к работе.

## Норма поставки на стороне чата

- Можно показать главную рекомендацию и ключевой shortlist.
- Обязательно сообщить, в какой файл записан результат.
- Если обнаружены проблемы старого варианта, кратко пояснить, «что исправлено на этот раз».
- Если включён Rubric, показать минимум пример оценок первых 3 мест для 1 платформы.
- Не повторять в чате всю большую таблицу, если пользователь явно не просит её посмотреть.

## Критерии успеха

Годный вариант названий как минимум должен удовлетворять:

- Читатель с первого взгляда понимает, что это название книги, а не рекламная фраза
- Способен охватить действительную основную торговую точку произведения, а не ухватить лишь мгновенную точку взрыва
- Внутри одной платформы нет повторяющихся заголовков; между платформами проведена глобальная дедупликация: среди m × n кандидатов названий нет ни одного повтора (требование уровня блокировки, при непрохождении поставка запрещена)
- У платформ есть явные различия в компромиссах
- Главная рекомендация обладает долговременной ценностью использования
- shortlist помогает пользователю быстро принять решение, а не продолжает топить его среди кандидатов
- Результат Rubric может объяснить «почему этот на первом месте, почему задние кандидаты понижены»; если сохранён внутренний разбор отсева, он также может объяснить, почему внутренние черновики отсеяны
