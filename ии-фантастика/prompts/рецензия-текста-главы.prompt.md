# ИИ-фантастика — рецензирование основного текста главы (специальный Prompt)

## Связанные навыки (специализированные для рецензии глав)

[`общий-рецензия-текста-главы`｜рецензирование основного текста главы](../skills/общий-рецензия-текста-главы/SKILL.md)

Для любой задачи «драйв продолжения чтения внутри главы / награда в середине / крючок в конце главы / согласованность с биографиями персонажей / системная честная дедукция (данные видимы, прослеживаемы, воспроизводимы) / аудит выпадения из образа из-за авторских номеров» следует в первую очередь вызывать этот skill.

> Общие правила и общие красные линии см.: `../agents/рецензент-романов.agent.md`. Этот файл содержит только «специальные для рецензирования основного текста главы» чек-листы, шаблоны и правила записи в хранилище.

## Целевое позиционирование (текст для читателя)
- Основной текст главы предназначен для читателя: главная цель — **чтобы читатель захотел продолжать читать / подписаться / комментировать**, и получил внутри главы явную награду.
- Но у этого жанра по-прежнему есть жёсткие инженерные ограничения: честная дедукция, носители цифровых следов, согласованность с биографиями персонажей, системное трение, хронология без дыр, и **в основном тексте не должно быть конкретного года**.
- При рецензировании давать два вида выводов:
	- Вывод читателя: каков основной эффект главы — «爽 / страх / сомнение / ненависть / любовь»? Причина продолжать читать — одной фразой.
	- Инженерный вывод: есть ли блокирующий публикацию P0 (например, конфликт биографий персонажей, обрыв цепочки данных).

## Различение рабочего файла и слоя публикации (обязательно)
- По умолчанию считать файл главы **рабочим контейнером автора**: если в одном `.md` одновременно есть `основной текст главы`, `## 作者有话说`, `## 章节后记`, `## 润色说明`, **это само по себе не проблема**.
- Объект рецензирования по умолчанию — **слой, видимый читателю**: `основной текст главы` и `## 作者有话说`; `послесловие к главе / пояснение шлифовки` читаются только как авторские записи и материалы аудита.
- **Нельзя лишь на основании** того, что `послесловие к главе / пояснение шлифовки` находятся в одном файле с основным текстом, признавать P0 / P1 / «нельзя публиковать».
- «Можно ли публиковать» по умолчанию означает **может ли основной текст перейти в последующий процесс публикации / процесс вывода на несколько платформ**, и **не равно** «исходный рабочий файл `.md` можно отдавать читателям «голым» напрямую».
- Только в следующих случаях `послесловие к главе / пояснение шлифовки` перечислять как проблему:
	1. это авторское содержимое подмешано в основной текст, эпиграф главы или `## 作者有话说`;
	2. пользователь явно требует рецензировать «итоговую публикуемую версию, которую можно сразу показать читателям / файл для прямой выдачи «голым» / итоговый вариант для платформы»;
	3. это авторское содержимое нарушает границы автоэкспорта, платформенной нарезки или скриптов статистики.

## Подтвердить перед началом (если чего-то нет — сначала спросить)
1) Путь к файлу основного текста целевой главы (относительный путь в репозитории)
2) Путь к плану тома / единицы-дела, к которому относится (как минимум план тома; если нет — пояснить отсутствие)
3) Список персонажей, появляющихся в главе (если пользователь не дал, вы обязаны сами извлечь из основного текста и перечислить)
4) Стратегия вывода в этот раз: перезапись | добавление рецензии этого раунда (по умолчанию — добавление)

## Цепочка чтения (специально для главы | сверху вниз)
В начале отчёта обязательно «подтверждение цепочки чтения» с заполнением путей:

1) `/.github/prompts/проектирование-плана.prompt.md`
2) Исследования письма (отметить 1–3 по фактическому наличию в проекте): `/写作研究/...`
3) Общий план (если существует): [путь]
4) План тома, к которому относится (обязательно): [путь]
5) Реестры (если существуют, как минимум один из): реестр улик / пул подозреваемых / временная ось
6) Биографии персонажей, появляющихся в главе (обязательно сверить по одной): `/人物传记/имя персонажа.md`
7) Основной текст целевой главы (обязательно): [путь]

Отсутствие любого вышестоящего звена: обязательно написать «точка блокировки / замещающее основание / риск».

## Текущая базовая линия образцовых глав (для сопоставления, специально для главы)
Если в проекте ведётся базовая линия образцовых глав, в отчёте перечислить результаты сопоставления:
- Образцовая глава A: аномальный старт (базовая линия «золотых трёх глав»)
- Образцовая глава B: честная дедукция и опровержение приговора (базовая линия замыкания улик)
- Образцовая глава C: давление атмосферы и цена (базовая линия триллера и последствий)

Если ещё не ведётся: в отчёте пометить «базовая линия образцовых глав не накоплена, в этом раунде рецензия по общим стандартам».

## Нормы вывода и записи в хранилище (специально для главы)
- Обязательный путь (есть части): `审阅意见/第X部/第Y卷/章节审阅报告_第X部_第Y卷_第Z章_YYYY-MM-DD.md`
- Обязательный путь (нет частей): `审阅意见/第X卷/章节审阅报告_第X卷_第Y章_YYYY-MM-DD.md`
- Перед записью файла необходимо сначала по пути основного текста целевой главы, плану тома или структуре каталогов проекта подтвердить метки `第X部 / 第Y卷 / 第Z章`, нельзя прямо откатываться в корневой каталог `审阅意见/`.

Отказоустойчивость: если отчёт положен не в тот каталог тома, вверху отчёта обязательно записать «путь к основному тексту целевой главы» и в начале пометить «исправление каталога».

Вывод «можно публиковать / нельзя публиковать» в отчёте по умолчанию пишется в рамках **слоя, видимого читателю**; если в этом раунде дополнительно проверялось «можно ли исходный рабочий файл отдавать «голым» напрямую», обязательно явно указать, что это **дополнительный вывод**, и он не может перекрывать вывод о качестве основного текста.

### Обязанности, сохраняемые этим Prompt

- Подтвердить целевой основной текст, план тома, список выступающих персонажей и стратегию вывода
- Сохранить читательскую цепочку, перекрёстную сверку реестров / биографий и ограничения путей внесения в библиотеку
- Принудительно требовать, чтобы рецензия главы одновременно давала «читательский вывод + инженерный вывод»
- Если есть контрольная карта или чёткий вышестоящий план главы, по умолчанию дополнительно нужно сверить «выполнено ли обещание контрольной карты», чтобы рецензия не смотрела только на текущий вариант, не глядя на цель строительства.

### Минимальные требования к выводу

- Структура отчёта обязательно следует `CommonSkills/общий-рецензия-текста-главы/references/полный-шаблон-рецензии-текста-главы.md`, нельзя понижать до упрощённого каркаса
- Рецензия должна охватывать: структуру внутри главы, согласованность с биографиями персонажей, привязку к тому, честную дедукцию, цепочку данных, объём знаков и красные линии выпадения из образа
- Рецензия должна охватывать `## 7. 🥊 竞对章节对照与补丁优先级` («Сопоставление глав с конкурентами и приоритеты патчей»), `## 7.1 竞对差距量化卡` («Карта количественной оценки разрыва с конкурентами») из полного шаблона и расчёт оценки по конкурентам со взвешиванием, их нельзя опускать
- Поле объёма знаков обязательно явно фиксирует исходные выводимые пункты `scripts/count-chapter.ps1` / `scripts/count-afterword.ps1`, нельзя заменять их самодельной сводкой Length / CJK
- Если есть проблема уровня P0, необходимо чётко написать вывод о блокировке публикации и минимальный замкнутый цикл исправлений
