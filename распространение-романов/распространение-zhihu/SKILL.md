# Загрузка указанных глав в Zhihu с сохранением рукописи

Используется, чтобы загрузить указанную вами 1 или несколько глав в соответствующее произведение авторского кабинета Zhihu и сохранить все как рукописи.


<!-- ===== Layer 3: кэш сценария ===== -->

## Правило маршрутизации рабочего каталога (обязательно)

Перед выполнением этого Skill необходимо определить рабочий каталог по следующим правилам:

1. **Прочитать `Agents.md` в корне проекта** и проверить в нём объявление `主输出平台` («основная платформа вывода»)
2. Если текущая платформа (Zhihu) совпадает с `主输出平台` → рабочий каталог — `小说正文/`
3. Если текущая платформа не совпадает с `主输出平台`, либо `Agents.md` не существует / `主输出平台` не объявлена → рабочий каталог — `知乎/`

Все последующие пути к файлам глав, README.md и 分发记录.md (журнал распространения) строятся от этого рабочего каталога. **Явно уточняется**:
  - **Когда эта платформа — основная платформа вывода** → файлы глав, `README.md`, `分发记录.md` находятся в `小说正文/`
  - **Когда эта платформа — не основная платформа вывода** → файлы глав, `README.md`, `分发记录.md` находятся в `知乎/`

> **О путях**: все пути вида `知乎/` в нижеследующих разделах (например, `知乎/README.md`, `知乎/分发记录.md`) приведены как примеры написания рабочего каталога. Фактический каталог определяется приведённым выше «Правилом маршрутизации рабочего каталога»: если эта платформа — основная платформа вывода, все эти пути соответствуют `小说正文/`; если нет — `知乎/`.

## Когда использовать

- Вы уже положили главы для загрузки в каталог `知乎/`.
- Вы уже записали в `知乎/README.md` аккаунт, пароль, ID книги Zhihu и название книги.
- Вы хотите, чтобы по фиксированному процессу автоматически выполнялось: вход → переход в управление произведениями → определение режима создания / изменения → заполнение заголовка и текста главы → сохранение рукописи → запись ID главы обратно.

## Случаи, когда не применяется

- Вы хотите лишь отшлифовать текст и не нуждаетесь в открытии сайта для загрузки.
- Вы не предоставили аккаунт Zhihu или ID книги.
- Цель — не «сохранить рукопись», а «опубликовать / выложить».

## Требования ко входным данным (обязательно)

### 1) Каталог файлов глав

- Файлы для загрузки должны лежать в `知乎/`.
- Вы явно указываете, какие главы загружать (одну или несколько).
- Заголовок главы **не берётся напрямую из имени файла**: его необходимо извлечь из содержимого файла главы, нормализовать и затем внести в поле заголовка на странице.

### 1.1) Правила извлечения и сборки заголовка главы (обязательно)

- Из файла главы обязательно извлечь: номер главы (арабскими цифрами), заголовок главы, основной текст.
- Если строка заголовка файла главы — `# 1.1.3 三分钟`, где `1.1.3` означает `номер части.номер тома.номер главы`; при извлечении необходимо взять только последний сегмент `3` как исходный номер главы, а `三分钟` — как «заголовок главы».
- В поле заголовка Zhihu следует вносить только текст заголовка `三分钟` или его сжатый вариант; если позже в журнале распространения или при вычислении абсолютного номера понадобится нумерация, также можно использовать только последний сегмент номера `3`, нельзя записывать в поле заголовка `1.1.3` как есть.
- Поле заголовка главы Zhihu — **единое поле ввода**, и по фактической проверке у него есть **лимит 15 знаков**.
- Заполнение заголовка должно в первую очередь обеспечивать возможность сохранения на платформе:
   - в первую очередь использовать краткий текст заголовка (рекомендуется без префикса `第X章`), укладываясь в 15 знаков.
   - если исходный заголовок превышает лимит, его необходимо сначала сжать, а затем выполнять сохранение рукописи.
- Информацию о томе / номере главы не обязательно записывать в поле заголовка Zhihu, согласованность соответствия «номер тома / номер главы / название главы» следует поддерживать через журнал распространения.

### 2) Источник метаданных

- Обязательно прочитать `知乎/README.md` и извлечь как минимум следующее:
  - имя пользователя Zhihu
  - пароль Zhihu
   - ID книги романа на Zhihu (только цифры, например `11997642`; выбрать значение, соответствующее текущей главе, по «правилу определения ID книги»)
   - название романа (название книги, для текущей цели загрузки)
### 2.1) Проверка платформы (обязательно)

После чтения `知乎/README.md` необходимо проверить, равен ли его первый заголовок первого уровня `# 知乎распространение-романов配置`:
  - **Совпадает** → продолжить последующий процесс
  - **Не совпадает** → немедленно остановить загрузку и сообщить пользователю об ошибке: `README.md 平台标识与当前 Skill 不符：预期"知乎распространение-романов配置"，实际读取到"{实际读取到的标题}"。请检查是否将其他平台的 README.md 误放到了当前工作目录。` (Идентификатор платформы в README.md не соответствует текущему Skill: ожидалось «知乎распространение-романов配置», фактически прочитано «{фактически прочитанный заголовок}». Проверьте, не положен ли в текущий рабочий каталог README.md другой платформы.)
### 3) Источник журнала распространения (обязательно)

- Обязательно прочитать `知乎/分发记录.md`:
  - если файла нет, сначала создать его, затем выполнять распространение.
  - используется для запроса соответствия «глава -> ID главы» и определения для главы «режима создания» или «режима изменения».

### 4) Правило определения названия книги (обязательно)

- Если у романа нет частей: название книги берётся из «названия романа (названия книги)» в `README.md` каталога этой платформы.
- Если у романа есть части (несколько частей): название книги — название той части, в которой находится глава; нельзя ошибочно использовать общее название.

### 4.1) Правило определения ID книги (обязательно)

- Если у романа нет частей: ID книги берётся из парной записи к «названию романа (названию книги)» в `README.md` каталога этой платформы.
- Если у романа есть части (несколько частей): ID книги берётся из парной записи к названию той части, в которой находится глава.
- Запрещено использовать ID книги общего названия для глав частей или ID книги одной части для глав другой части.

### 5) Шаблон `分发记录.md` (при первом создании использовать напрямую)

```markdown
# 知乎распространение-романов记录

> Назначение: фиксирует соответствие «уникальный ключ главы -> ID главы Zhihu», чтобы процесс распространения мог определять «режим создания / режим изменения».

## Описание полей

- `章节唯一键` (уникальный ключ главы): фиксированный формат `知乎书籍ID|分部名|卷号|章号|章名` (если частей нет, в поле названия части пишется `NA`)
- `知乎书籍ID` (ID книги Zhihu): соответствует ID книги в `知乎/README.md`
- `章节Id` (ID главы): параметр `id` в адресе редактирования главы Zhihu (только цифры)
- `最近操作` (последняя операция): `新建` (создание) или `修改` (изменение)
- `更新时间` (время обновления): `YYYY-MM-DD HH:mm:ss`
- `备注` (примечание): необязательно

## Таблица записей

|章节唯一键|知乎书籍ID|章节Id|最近操作|更新时间|备注|
|:--|--:|--:|:--|:--|:--|
```

## Процесс выполнения (строго по порядку)

### Шаг 1: чтение локальных входных данных

1. Прочитать и разобрать `知乎/README.md`.
2. Убедиться, что получены: аккаунт, пароль, целевой ID книги (выбранный по «правилу определения ID книги»), целевое название романа.
3. Прочитать `知乎/分发记录.md` и построить соответствие «уникальный ключ главы -> ID главы» (рекомендуемый уникальный ключ: `知乎书籍ID|分部名|卷号|章号|章名`; если частей нет, название части фиксированно `NA`).
4. Прочитать указанные вами файлы глав и извлечь для каждой главы: номер тома, номер главы (арабскими цифрами), заголовок главы, основной текст.

### Шаг 1.5: вычисление абсолютного номера главы (по схеме Qimao)

1. Нумерация глав везде использует «абсолютный номер главы», локальная нумерация не применяется.
2. Способ вычисления:
   - прочитать из `分发记录.md` все записанные главы под тем же целевым ID книги;
   - отсортировав по `卷号` (номеру тома) и `章号`, вычислить абсолютный порядковый номер текущей главы во всей книге.
3. Для сценария публикации в Zhihu без деления на тома номер главы использует абсолютный номер, формула расчёта:
   - `абсолютный номер главы = сумма числа глав предыдущих томов + относительный номер этой главы в её томе`.
4. Пример:
   - если в томе 1 — 90 глав, а в томе 2 — 100 глав:
   - том 1, глава 5 → абсолютный номер главы: глава 5;
   - том 2, глава 5 → абсолютный номер главы: глава 95;
   - том 3, глава 5 → абсолютный номер главы: глава 195.
5. Если `分发记录.md` не существует или в нём нет истории записей, вычислять по приведённой формуле из известной структуры томов и глав; если число глав предыдущих томов определить нельзя, сначала нужно восполнить реестр и только потом публиковать.
6. Абсолютный номер главы в основном используется для журнала распространения и проверки, обязательно записывать его в поле заголовка на сайте не требуется.

### Шаг 2: вход в авторский кабинет Zhihu

1. **Обязательно открыть новую вкладку браузера** и в этой новой вкладке перейти по адресу:
   - `https://www.zhihu.com/author-platform/home/management`
2. Эта новая вкладка используется только для текущего процесса загрузки в Zhihu; вкладку, в которой вы сейчас решаете другие задачи, повторно не использовать.
3. Если появляется состояние «не выполнен вход»:
   - после перехода к процессу входа выбрать «密码登录» (вход по паролю).
   - ввести имя пользователя и пароль из `README.md` и завершить вход.
4. После успешного входа обязательно оставаться на странице управления произведениями:
   - `https://www.zhihu.com/author-platform/home/management`

### Шаг 3: переход в управление произведениями и поиск целевого произведения (предпосылка режима создания)

> Этот шаг — жёсткая предпосылка создания главы в Zhihu: **новую главу нельзя открыть ручной правкой URL, необходимо войти через кнопку «增加小节» (добавить раздел) в левом нижнем углу страницы.**

1. На странице управления произведениями выбрать «中长篇作品» (средние и длинные произведения).
2. В списке произведений найти целевое произведение:
   - в столбце названия произведения показывается «название произведения + ID произведения».
   - название произведения кликабельно.
3. Нажать название целевого произведения, чтобы войти на страницу редактирования содержимого.
4. В левом верхнем углу страницы редактирования содержимого проверить, совпадает ли название книги с целевым названием из `README.md`.
   - При несовпадении немедленно остановиться, продолжать загрузку нельзя.
5. Если после входа появляются слои вроде «编辑器使用说明» (инструкция по использованию редактора):
   - сначала закрыть слой, затем выполнять «добавить раздел / заполнить основной текст / сохранить рукопись».
   - до закрытия слоя нельзя ошибочно считать, что кнопка неисправна или страница изменилась.

### Шаг 4: разведение создания / изменения

1. Перед началом каждой главы сначала проверить `知乎/分发记录.md`:
   - если уже есть `章节Id`: идти по **режиму изменения**.
   - если нет `章节Id`: идти по **режиму создания**.

2. Режим изменения:
   - перейти напрямую: `https://www.zhihu.com/author-platform/writer?id={章节Id}&step=2`
   - ещё раз убедиться, что страница по-прежнему принадлежит целевой книге.

3. Режим создания (входить обязательно через кнопку):
   - на странице редактирования содержимого целевого произведения нажать кнопку «增加小节» в левом нижнем углу.
   - после перехода откроется адрес новой главы, URL вида:
     - `https://www.zhihu.com/author-platform/writer?id={章节Id}&step=2`
   - извлечь из URL только что созданный `{章节Id}` (только цифры).

### Шаг 5: заполнение заголовка и основного текста главы

1. Сначала подтвердить абсолютный номер текущей главы (из шага 1.5).
2. В поле заголовка главы внести соответствующий требованиям платформы заголовок (рекомендуется без префикса `第X章`).
3. Обязательно убедиться, что длина заголовка не превышает 15 знаков (в интерфейсе обычно показывается как `X/15`).
4. Если заголовок превышает лимит (например, `27/15`), сначала сжать заголовок и только затем сохранять рукопись.
5. В область редактирования основного текста вставить основной текст этой главы.
6. В Zhihu нет области ввода «слова от автора», **не пытайтесь заполнять слово от автора**.

### Шаг 6: сохранение рукописи и запись обратно

1. Нажать кнопку «保存稿件» (сохранить рукопись) в нижней части страницы.
2. **После нажатия обязательно подождать и прочитать информацию обратной связи в верхней части страницы** (нельзя сразу переключаться на другую главу):
   - подождать не менее `2–5` секунд и посмотреть, появилось ли вверху «保存成功 / 已保存到云端» (успешно сохранено / сохранено в облаке) или эквивалентное сообщение об успехе.
   - если сообщение об успехе не появилось или появилось только сообщение о сбое / аномалии, главу нельзя записывать как успешную.
   - если сообщение кратковременно исчезло, нужно на текущей странице запустить сохранение ещё раз и перепроверить текст сообщения.
3. Записать «уникальный ключ главы + ID главы + время обновления» обратно в `知乎/分发记录.md`:
   - если записи нет: добавить новую.
   - если запись уже есть: обновить `章节Id` (если изменился) и время обновления.

### Шаг 7: цикл по нескольким главам (особенность Zhihu)

- Для каждой указанной главы повторять шаги 4–6, пока не будут завершены все главы.
- **Обязательное правило**: когда нужно продолжить создание следующей главы, нельзя полагаться на ручную правку URL для входа на страницу создания; обязательно вернуться на страницу редактирования содержимого произведения, снова нажать кнопку «增加小节» в левом нижнем углу и получить новый URL главы и новый ID главы.
- Только для «изменения уже существующей главы» разрешён прямой вход по URL `writer?id={章节Id}&step=2`.


### Режим ускорения для непрерывных нескольких глав (рекомендуется)

> Цель: без ослабления действующих обязательных правил сократить затраты на повторные клики, повторные вставки и повторные определения.

#### A. Сначала пакетная предобработка, затем непрерывное выполнение в браузере

- Перед открытием страницы разом выполнить следующую предобработку:
   - извлечение номера / заголовка главы;
   - разделение основного текста и расширенных полей платформы (например, «слово автора» / текст настроек публикации);
   - предпроверка ограничений платформы (например, число знаков в заголовке, число знаков в слове автора, обязательные пункты публикации);
   - предварительное определение режима создания / изменения (по `分发记录.md`).
- Рекомендуется складывать результаты в единую временную очередь (например, объект в памяти либо `{каталог платформы}/.cache/content_parts/no_part/v{номер тома}/*.txt`, `{каталог платформы}/.cache/content_parts/p{номер части}/v{номер тома}/*.txt` + таблица соответствий); на стадии браузера выполняется только «взять данные → заполнить → сохранить».

#### B. На стадии браузера использовать «фиксированный вход + повторяющийся такт»

- Для каждой главы сохранять единый такт:
   1) открыть целевой адрес (по записи — создание или изменение);
   2) заполнить заголовок;
   3) заполнить основной текст;
   4) заполнить расширенные поля платформы (например, слово автора / настройки публикации);
   5) сохранить черновик;
   6) извлечь ID главы;
   7) записать запись обратно.
- Кроме «целевого адреса» и «вносимого текста», остальные действия по возможности держать в одном наборе локаторов и в одном порядке, избегая смены стратегии на каждой главе.

#### C. Вместо «разовой отправки всей партии» использовать «малые партии»

- Рекомендуется выполнять малыми партиями по `5–10` глав:
   - после завершения каждой малой партии сразу записывать обратно в `分发记录.md`;
   - затем переходить к следующей малой партии.
- Так даже при ограничении частоты, колебаниях состояния входа или смене вёрстки страницы пострадает только текущая малая партия, а прогресс всей партии не откатится.

> Три раздела D / E / F исполняются по единому правилу: в приоритете непрерывность партий и возможность отката; подсказки о проверке безопасности всегда считать блокирующими; сбои канала данных должны допускать деградацию.

#### D. Однократное «шумоподавление» для «частых всплывающих окон»

- Для неблокирующих напоминаний, многократно появляющихся на платформе (напоминание о числе знаков, обучающие слои, окна-подсказки), при первом появлении можно убрать шум и продолжить основной процесс.
- Только когда всплывающее окно реально блокирует критический путь «ввод / сохранение / отправка», повышать до обработки как сбой или ручного вмешательства.

#### E. Многоуровневая обработка сбоев: быстро пропустить, можно продолжить

- При сбое отдельной главы применять стратегию «записать причину и перейти к следующей главе» (если пользователь не требует остановки при первой ошибке).
- Для сбойной главы нужно зафиксировать минимально необходимую информацию:
   - уникальный ключ главы;
   - шаг сбоя (открытие страницы / заголовок / текст / расширенные поля платформы / сохранение / запись обратно);
   - ключевая подсказка страницы.
- После завершения партии догружать главы по списку сбоев отдельно, не застревая на них в основном цикле.

#### F. Ускорение канала данных (по желанию)

- В сценариях длинной пакетной автоматизации можно использовать `scripts/content_parts_server.mjs`:
   - без частей: `/parts/v/{номер тома}/{номер главы}`
   - с частями: `/parts/p/{номер части}/v/{номер тома}/{номер главы}`
   - плоский `/parts/{номер главы}` допустим только для временного использования в одной партии.
- Этот способ — средство ускорения; он не заменяет требования каждого платформенного Skill к определению ID книги, уникальному ключу главы, правилам записи обратно и обработке сбоев.

#### G. Патч защиты от неправильного применения при пакетном выполнении (рекомендуется включать по умолчанию)

- «Предварительное определение режима создания / изменения» служит только ускорению и не заменяет запрос к `分发记录.md` в реальном времени перед выполнением каждой главы.
- «Шумоподавление частых всплывающих окон» допускается только для небезопасных подсказок; если речь о контроле риска при входе, капче, проверке реального имени, подсказках безопасности аккаунта — всегда считать блокировкой и приостанавливать.
- В многоуровневую обработку сбоев нужно добавить «остановку при фатальной ошибке»: при несовпадении названия книги / тома (или произведения), ошибочном ID книги, неснятой аномалии состояния входа продолжать к следующей главе нельзя.
- При использовании канала данных (например, `content_parts_server`) обязательно предусмотреть путь деградации: при недоступности сервиса автоматически откатываться на чтение локальных файлов, не прерывая выполнение партии.
- В конце каждой малой партии обязательно выполнять сверку: `плановое число глав = число успешных глав + число сбойных глав`, причём для всех успешных глав должна быть выполнена запись `章节Id` обратно.

## Обработка сбоев и откатов

- Сбой входа: сообщить об ошибке аккаунта / пароля и остановиться, не продолжая последующие главы.
- Появилась вторичная проверка (капча / слайдер): обязательно немедленно приостановить процесс, дождаться, пока пользователь вручную завершит проверку и явно сообщит «登录完成»; до получения этой обратной связи любые последующие шаги выполнять нельзя.
- Если после входа снова срабатывает вторичная проверка (интерфейс 400/403 или окно проверки): по-прежнему действовать по правилу «обязательно приостановиться и ждать обратной связи о завершении входа», нельзя считать состояние входа вечно действительным.
- Отсутствие элемента страницы (например, изменение кнопки «中长篇作品» или «增加小节»): записать шаг сбоя и остановить эту главу.
- Ключевой слой перекрывает кнопку (например, «编辑器使用说明») и нажать нельзя: сначала закрыть слой и повторить; лишь если сбой остаётся — обрабатывать как «отсутствие элемента страницы».
- Проверка названия книги не совпала: сразу остановить процесс загрузки этой книги, слепая загрузка запрещена.
- Сбой «保存稿件»: отметить главу как сбойную; если после повторной попытки сбой остаётся — сохранить запись о сбое и перейти к следующей главе (если пользователь не требует остановки при первой ошибке).
- После «保存稿件» ясного сообщения об успехе не видно: статус главы записывается как «успех не подтверждён», на текущей странице главы обязательно сохранить повторно и прочитать верхнюю обратную связь; если по-прежнему не подтверждено — записать сбой, в реестр успеха не записывать.
- Сбой записи `分发记录.md`: процесс помечается как «частичный сбой (запись не записана на диск)» и предлагается ручная дозапись.

## Накопленный практический опыт (Zhihu)

- Сначала завершить «中长篇作品 + вход по клику на название произведения + проверка названия книги в левом верхнем углу», затем заполнять основной текст — это заметно снижает риск загрузки не в ту книгу.
- При создании главы `id` в `writer?id={章节Id}&step=2` и есть ID главы, после сохранения его нужно сразу записать обратно.
- При непрерывном создании нескольких глав для каждой главы заново нажимать «增加小节», чтобы получить новый ID главы; не переиспользовать URL предыдущей страницы создания.
- Поле заголовка редактора Zhihu по фактической проверке имеет лимит 15 знаков; превышение мешает стабильному сохранению, нужно сначала сжать заголовок и только потом нажимать «保存稿件».
- При первом входе на страницу может появиться слой «编辑器使用说明», который перекрывает кнопки вроде «增加小节 / 保存稿件»; сначала обязательно закрыть слой.
- Сигналом завершения каждой главы считать единственно подсказку об успешном «保存稿件»; без подсказки об успехе глава не считается завершённой.
- После «保存稿件» не переходить сразу к следующей главе; сначала следить за верхней обратной связью, а затем определять успех.
- Записи в журнале автоматизации вроде «обработано / нажато сохранение» не заменяют сигнал успеха на странице; запись в реестр может происходить только после сигнала успеха.

## Разбор текущего пакетного прогона (2026-05-21)

### Удачный опыт

- Перед пакетом сначала завершить «предобработку глав (сжатие заголовка до 15 знаков + удаление слова от автора из основного текста)» — это заметно сокращает ошибки на этапе сохранения.
- Сначала переключиться на «中长篇作品» и войти в целевое произведение, затем в цикле «добавить раздел → заполнить → сохранить рукопись» — стабильность выше, чем при попытке угадывать состояние страницы по URL.
- После создания каждой главы сразу извлекать `章节Id` из `writer?id={章节Id}&step=2` — это позволяет избежать сдвига соответствий при последующей записи.

### Выявленные проблемы

- Одни скриптовые подсчёты (например, «обработано столько-то глав») могут приводить к ошибочным суждениям; это не равно «действительно сохранено успешно».
- В сценарии быстрой пакетной загрузки, если сразу после нажатия «保存稿件» переключиться на другую главу, можно пропустить верхнюю обратную связь, что даёт скрытый сбой вида «нажато, но не сохранено».

### Исправленные обязательные нормы

- После нажатия «保存稿件» для каждой главы обязательно подождать и прочитать текст верхней обратной связи страницы; пока нет явного сообщения об успехе, признавать успех запрещено.
- Правило подсчёта «числа успешных глав» необходимо изменить на: **получена верхняя подсказка об успехе + текущая страница writer доступна для повторного захода + ID главы записан в реестр** — все три условия одновременно.
- Если любое условие не выполнено, глава попадает в список сбоев или список на догрузку и не может смешиваться с подсчётом успешных.
